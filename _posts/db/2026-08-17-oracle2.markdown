## 안녕하십니까! 😀

대용량 데이터를 처리하다 보면 테이블 크기가 수천만 건에서 수억 건 이상으로 불어나면서 단순 인덱스만으로는 감당하기 어려운 성능 저하나 I/O 병목 현상을 마주하게 됩니다.

특히 특정 시점이나 특정 파티션에 쓰기(Write/Insert) 부하가 집중되어 경합(Contention)이 발생할 때, **오라클의 해시 파티셔닝(Hash Partitioning)**은 매우 강력한 해결책이 되어줍니다.

오늘은 파티셔닝의 기본 개념부터 주요 종류별 장단점, 그리고 실무에서 **해시 파티셔닝을 통해 대용량 처리 부하를 획기적으로 개선한 사례**를 정리해보겠습니다!

---

## 1. 파티셔닝(Partitioning)이란?

**파티셔닝(Partitioning)**은 수천만 건 이상의 대용량 테이블이나 인덱스를 관리하기 용이한 작은 단위(파티션)로 물리적으로 분할하는 기법입니다.

- **논리적 관점**: 사용자와 애플리케이션 입장에서는 여전히 하나의 단일 테이블로 보이며, 기존 SQL을 그대로 사용합니다.
- **물리적 관점**: 내부적으로 각 파티션이 서로 다른 세그먼트(Segment)나 테이블스페이스(Tablespace)에 분할 저장됩니다.

### 파티셔닝의 핵심 이점
1. **성능 향상 (Partition Pruning)**: 쿼리 조건에 해당하는 파티션만 골라서 조회하고 나머지 불필요한 파티션은 아예 스캔 대상에서 제외하므로 I/O를 획기적으로 절감합니다.
2. **가용성 증대 (High Availability)**: 특정 파티션이 손상되거나 백업/복구 중이더라도 다른 파티션은 정상적으로 읽기/쓰기가 가능합니다.
3. **관리 용이성 (Manageability)**: 오래된 이력 데이터를 삭제할 때 무거운 `DELETE` 대신 파티션 단위 `DROP / TRUNCATE`를 사용하여 즉각적이고 부하 없이 처리할 수 있습니다.
4. **경합 분산 (Contention Reduction)**: 데이터를 물리적인 디스크나 블록 단위로 고르게 분산하여 동시 다발적인 쓰기 트래픽의 버퍼 캐시 경합을 완화합니다.

---

## 2. 파티셔닝의 종류와 장단점 비교

오라클 DB에서 제공하는 대표적인 파티셔닝 방식들과 각각의 장단점을 살펴보겠습니다.

### 1) 레인지 파티셔닝 (Range Partitioning)
지정한 컬럼의 **값 범위(날짜, 숫자 등)**를 기준으로 분할하는 가장 대중적인 방식입니다.

```sql
CREATE TABLE TB_ORDER_HIST (
    ORDER_ID   NUMBER,
    ORDER_DATE DATE,
    AMOUNT     NUMBER
)
PARTITION BY RANGE (ORDER_DATE) (
    PARTITION P_202601 VALUES LESS THAN (TO_DATE('2026-02-01', 'YYYY-MM-DD')),
    PARTITION P_202602 VALUES LESS THAN (TO_DATE('2026-03-01', 'YYYY-MM-DD')),
    PARTITION P_MAX    VALUES LESS THAN (MAXVALUE)
);
```

- **장점**: 
  - 시계열/이력성 데이터(로그, 주문 내역 등) 관리에 최적입니다.
  - 오래된 파티션 `DROP/TRUNCATE`로 보관 주기(Retention) 관리가 매우 쉽습니다.
- **단점**:
  - 최근 데이터 파티션 1개에만 Insert가 집중되는 핫스팟(Hotspot) 현상이 발생하기 쉽습니다.

---

### 2) 리스트 파티셔닝 (List Partitioning)
지정한 컬럼의 **특정 값 목록(코드값, 지역, 부서 등)**을 기준으로 분할합니다.

```sql
CREATE TABLE TB_CUSTOMER (
    CUST_ID   NUMBER,
    REGION    VARCHAR2(10),
    NAME      VARCHAR2(50)
)
PARTITION BY LIST (REGION) (
    PARTITION P_SEOUL VALUES ('SEOUL', 'GYEONGGI'),
    PARTITION P_BUSAN VALUES ('BUSAN', 'ULSAN'),
    PARTITION P_ETC   VALUES (DEFAULT)
);
```

- **장점**: 불연속적이거나 특정 그룹 코드로 데이터를 명확히 나눌 때 적합합니다.
- **단점**: 각 파티션 간 데이터 균등 분산이 어렵고, 새로운 코드값이 생기면 파티션 추가 관리가 필요합니다.

---

### 3) 해시 파티셔닝 (Hash Partitioning)
오라클 내부의 **해시 함수(Hash Algorithm)**를 사용하여 지정한 키 컬럼의 해시값에 따라 데이터를 각 파티션에 균등하게 분산 저장합니다.

```sql
CREATE TABLE TB_TX_LOG (
    TX_ID      VARCHAR2(32),
    USER_ID    NUMBER,
    TX_TIME    DATE,
    PAY_AMOUNT NUMBER
)
PARTITION BY HASH (TX_ID)
PARTITIONS 8;
```

- **장점**:
  - 데이터와 쓰기 I/O를 여러 파티션으로 **완벽하게 균등 분산**시켜 핫스팟 및 블록 경합을 원천 방지합니다.
  - 범위 기준이 뚜렷하지 않은 고유 키(UUID, 계좌번호, 트랜잭션ID 등) 기반 테이블에 적합합니다.
- **단점**:
  - 범위 검색(`BETWEEN`, `>`, `<`) 시 Partition Pruning 효과를 얻기 어렵습니다. (동등 조건 `=` 또는 `IN` 조건일 때만 Pruning 지원)
  - 특정 날짜 구간만 한 번에 잘라내는 식의 데이터 삭제 관리가 어렵습니다.

---

### 4) 컴포지트 파티셔닝 (Composite Partitioning)
위 방식들을 조합하여 2단계로 분할하는 방식입니다. (예: `Range-Hash`, `Range-List`)

- 예: 날짜(`Range`)로 1차 분할 후 각 월 내부에서 `Hash`로 2차 분할하여 이력 관리와 쓰기 분산 장점을 모두 취함.

| 파티션 종류 | 주요 용도 | Pruning 조건 | 균등 분산도 |
| :--- | :--- | :--- | :--- |
| **Range** | 날짜/일자별 이력 테이블 | 범위 & 동등 조건 | 낮음 (최신 파티션 집중) |
| **List** | 지역, 상태코드 등 그룹별 분할 | 동등 & IN 조건 | 보통 |
| **Hash** | 대량 트랜잭션 수집, 핫스팟 해소 | 동등(=), IN 조건 | **매우 높음 (균등 분할)** |
| **Composite** | 대용량 복합 요건 테이블 | 다차원 조건 | 높음 |

## 3. 해시 파티셔닝을 이용한 대용량 처리 부하 개선 사례

### 📌 문제 상황 (AS-IS)
실시간 결제 및 인증 트랜잭션 로그를 저장하는 테이블 `TB_PAYMENT_LOG`가 있었습니다.
- **일일 적재량**: 하루 약 3,000만 건 (초당 수천 건의 동시 INSERT 발생)
- **증상**: 
  1. 피크 시간대에 `buffer busy waits`, `enq: TX - index contention` 대기 이벤트가 심각하게 발생.
  2. 날짜 컬럼 기준의 Range 파티션 구조였기 때문에, **오늘 날짜의 단일 파티션과 인덱스 Leaf Block의 우측 끝에 모든 세션의 Write I/O가 집중**되면서 DB CPU 및 Lock 대기 급증.
  3. 트랜잭션 지연 및 타임아웃 발생.

```
[AS-IS 구조]
Range Partitioned by TX_DATE (하루 1개 파티션)
-> 오늘자 파티션(P_TODAY)에 수많은 세션이 동시 INSERT 몰림 (Hotspot 발생!)
```

---

### 💡 개선 방안 (TO-BE: Hash Partitioning 도입)

주요 조회 패턴이 `TX_ID`를 통한 건별 단건 조회 및 실시간 처리인 점에 착안하여, `TX_ID` 기반 **16개 해시 파티션(Hash Partition)**으로 재설계했습니다.
*(참고: 해시 파티션 개수는 2의 거듭제곱 수인 2, 4, 8, 16, 32... 로 설정해야 오라클 해시 알고리즘이 가장 균등하게 분배합니다.)*

#### 테이블 및 인덱스 리빌드 DDL

```sql
-- 해시 파티션 테이블 생성 (16개 파티션으로 분산)
CREATE TABLE TB_PAYMENT_LOG (
    TX_ID        VARCHAR2(64)  NOT NULL,
    USER_NO      NUMBER(12)    NOT NULL,
    PAY_AMOUNT   NUMBER(15)    NOT NULL,
    STATUS       VARCHAR2(10)  NOT NULL,
    TX_DATE      DATE          DEFAULT SYSDATE
)
PARTITION BY HASH (TX_ID)
PARTITIONS 16
STORE IN (TS_PAY_DATA01, TS_PAY_DATA02, TS_PAY_DATA03, TS_PAY_DATA04);

-- Local Partitioned Index 생성 (인덱스 블록도 16개로 분산)
CREATE UNIQUE INDEX PK_TB_PAYMENT_LOG ON TB_PAYMENT_LOG (TX_ID) LOCAL;

ALTER TABLE TB_PAYMENT_LOG 
ADD CONSTRAINT PK_TB_PAYMENT_LOG PRIMARY KEY (TX_ID)
USING INDEX PK_TB_PAYMENT_LOG;
```

---

### 📊 개선 결과 비교

| 항목 | AS-IS (Range 파티션) | TO-BE (16개 Hash 파티션) | 개선 효과 |
| :--- | :--- | :--- | :--- |
| **주요 대기 이벤트** | `buffer busy waits` (높음)<br>`enq: TX - contention` | `db file sequential read` (정상 범주) | **블록 경합 92% 감소** |
| **피크 타임 INSERT TPS** | 평균 2,100 TPS (지연 발생) | 평균 **5,800+ TPS** 안정적 처리 | **처리량 약 2.7배 향상** |
| **단건 조회 응답 시간** | 평균 15ms ~ 40ms (경합 시 튐) | 평균 **2ms 내외** 안정적 유지 | **응답 속도 대폭 안정화** |

#### 개선 포인트 정리
1. **물리적 동시 쓰기 분산**: 16개의 독립된 데이터 세그먼트와 로컬 인덱스 블록으로 Write I/O가 분산되어 특정 블록에 대한 동시성 락 경합이 완전히 해소되었습니다.
2. **테이블스페이스 다중화**: 4개의 물리 디스크 테이블스페이스(`TS_PAY_DATA01~04`)에 분산 배치하여 스토리지 레벨 I/O 큐 대기 시간도 단축시켰습니다.

## 4. 해시 파티셔닝 적용 시 주의할 점 & Best Practice

1. **파티션 개수는 반드시 2의 제곱수($2^n$)로 설정**
   - 2, 4, 8, 16, 32, 64 등의 개수로 지정해야 해시 버킷이 균등하게 매핑되어 데이터 편향(Skew)이 발생하지 않습니다.
2. **파티션 키(Partition Key)는 카디널리티가 높은 고유값 선택**
   - 중복도가 높은 코드값 대신 `PK`, `UUID`, `시퀀스 기반 ID` 등을 사용해야 고른 분산이 이루어집니다.
3. **Local Index 활용 권장**
   - 해시 파티션 테이블에는 글로벌 인덱스보다 파티션 구조와 1:1로 매핑되는 **Local Partitioned Index**를 생성해야 인덱스 쓰기 분산 효과를 100% 누릴 수 있습니다.
