## 안녕하십니까! 😀

현대 웹 서비스 아키텍처에서 빠지지 않고 등장하는 핵심 컴포넌트 중 하나가 바로 **Redis(Remote Dictionary Server)**입니다.

트래픽이 급증하고 빠른 응답 속도가 중요한 서비스 환경에서 RDBMS만으로는 병목 현상을 피하기 어렵습니다. 이때 Redis는 데이터베이스 부하를 줄이고 처리 성능을 비약적으로 끌어올리는 구원투수 역할을 합니다.

오늘은 **Redis의 기본 개념**, **웹 서비스에서 Redis를 필수적으로 사용하는 이유**, **실무 활용 사례**, 그리고 많은 분들이 고민하시는 **임시 저장소로서 NoSQL vs Redis 선택 기준**까지 알기 쉽게 정리해보겠습니다! 🚀

## 1. REDIS란?

**Redis(Remote Dictionary Server)**는 **인메모리(In-Memory)** 기반의 오픈소스 **키-값(Key-Value) 데이터 구조 저장소(Data Store)**입니다.

### 📌 Redis의 핵심 특징

1. **초고속 In-Memory 처리**
   - 모든 데이터를 디스크가 아닌 메인 메모리(RAM)에 저장하고 처리하므로 마이크로초(μs) 단위의 압도적인 읽기/쓰기 속도를 제공합니다.
2. **다양한 자료구조 지원**
   - 단순 문자열(String)뿐만 아니라 List, Set, Sorted Set(ZSet), Hash, Bitmaps, HyperLogLogs, Geospatial 등 풍부한 데이터 타입을 기본 지원합니다.
3. **싱글 스레드(Single-Threaded) 이벤트 루프 기반 동작**
   - 핵심 커맨드 처리가 싱글 스레드로 동작하여 Context Switching 오버헤드가 적고, 복잡한 락(Lock) 경합 없이 원자적(Atomic) 연산이 보장됩니다.
4. **영속성(Persistence) 지원**
   - 메모리 DB임에도 불구하고 스냅샷(RDB) 및 변경 로그 기록(AOF) 기능을 통해 서버 재시작 시 데이터를 복구할 수 있는 영속성 옵션을 제공합니다.

## 2. REDIS를 웹 서비스에서 사용하는 이유

웹 서비스 규모가 커질수록 다음과 같은 이유로 Redis를 도입하게 됩니다.

```
[클라이언트 요청] 
      │
      ▼
┌─────────────┐   Cache Hit (초고속 반환)
│  Web / WAS  │ ───────────────────────► ┌───────────────┐
└─────────────┘                          │  Redis Cache  │
      │                                  └───────────────┘
      │ Cache Miss / 쓰기 요청
      ▼
┌─────────────┐
│  Main DB    │ (RDBMS / Disk I/O 병목 완화)
│ (MySQL etc) │
└─────────────┘
```

### 1) RDBMS의 디스크 I/O 병목 및 커넥션 부하 경감
- 사용자가 몰릴 때 반복적인 DB 쿼리는 디스크 I/O와 DB CPU 점유율을 급증시킵니다.
- 자주 조회되지만 변경이 적은 데이터를 Redis에 캐싱(Caching)해두면, DB 부하를 80~90% 이상 절감할 수 있습니다.

### 2) 분산 서버 환경에서의 상태 동기화 (Stateless 아키텍처)
- 서버를 오토스케일링(Scale-out)할 때 각 서버 메모리에 세션을 두면 세션 불일치 문제가 발생합니다.
- 공용 Redis를 세션 저장소로 활용하면 모든 WAS 인스턴스가 동일한 세션 정보를 안정적으로 공유할 수 있습니다.

### 3) 원자적(Atomic) 연산을 통한 동시성 제어
- `INCR`, `SETNX` 같은 원자적 명령어를 통해 멀티 인스턴스 환경에서도 Race Condition 없이 정확한 카운팅이나 동시성 제어가 가능합니다.

## 3. REDIS 실무 사용 사례

실제 서비스 개발 및 운영 현장에서 Redis가 가장 활발하게 쓰이는 대표적인 4가지 사례입니다.

### ① 캐싱(Caching) 레이어
- **조회 성능 극대화**: 상품 상세 정보, 메인 페이지 배너/공지사항, 공통 코드성 데이터 등을 캐싱하여 밀리초 미만의 응답을 보장합니다.
- **Cache-Aside / Write-Through 전략**: 애플리케이션 요구에 맞춰 적절한 캐시 갱신 전략을 구성합니다.

### ② 분산 세션 관리 (Session Store) & 인증 토큰 저장
- **로그인 세션 유지**: Spring Session Redis 등을 이용하여 다중 서버 환경에서 세션을 공유합니다.
- **JWT Refresh Token 관리**: TTL(Time-To-Live) 기능을 이용해 리프레시 토큰의 만료 시간을 자동으로 관리하고, 로그아웃 시 블랙리스트 처리에도 활용합니다.

### ③ 실시간 랭킹 & 순위표 (Leaderboard)
- **Sorted Set(ZSet)** 자료구조 활용: 점수(Score)를 기반으로 데이터가 자동 정렬되므로 `ZADD`, `ZRANGE`, `ZREVRANK` 명령어로 실시간 게임 랭킹, 실시간 인기 검색어, 조회수 랭킹 등을 $O(\log N)$ 시간 복잡도로 빠르게 처리할 수 있습니다.

### ④ 분산 락(Distributed Lock) & API Rate Limiter
- **선착순 이벤트 / 재고 차감**: 여러 서버에서 동시에 재고를 차감하거나 쿠폰을 발급할 때, Redis의 `SETNX` 또는 Redisson 분산 락을 사용하여 중복 처리를 방지합니다.
- **요청 제한(Rate Limiting)**: 특정 IP/사용자별 분당 요청 횟수를 제한하여 DDoS 공격 및 비정상 트래픽을 차단합니다.

## 4. 임시 저장소로 NOSQL과 REDIS 중 어떤 걸 사용해야 할까?

프로젝트를 진행하다 보면 "임시 데이터 저장소로 MongoDB/DynamoDB 같은 NoSQL을 쓸까, Redis를 쓸까?" 고민하는 상황을 마주하게 됩니다.

두 기술의 특성을 비교하여 선택 기준을 정리해 드립니다.

### 📊 Redis vs Disk 기반 NoSQL 비교

| 비교 항목 | Redis (In-Memory K-V) | 일반 NoSQL (MongoDB, DynamoDB 등) |
| :--- | :--- | :--- |
| **주 저장 위치** | **메인 메모리 (RAM)** | **디스크 (SSD/NVMe) + 메모리 버퍼** |
| **처리 속도** | **초고속 (Sub-millisecond)** | 빠름 (수 ms ~ 수십 ms) |
| **데이터 만료 (TTL)** | **키 단위 정밀 자동 만료 (강력)** | TTL 인덱스 지원 (배치 주기에 따라 약간 지연 가능) |
| **데이터 용량 한계** | RAM 용량 제한 (비용 높음) | 디스크 기반으로 대용량/확장에 유리 (비용 효율적) |
| **쿼리 유연성** | Key 기반 접근 및 전용 자료구조 | 복잡한 조건 검색, 다중 인덱스, 집계(Aggregation) 지원 |
| **데이터 영속성 신뢰도** | 휘발 가능성 고려 필요 (캐시/임시 적합) | 강력한 영속성 및 트랜잭션/복제 지원 |

---

### 💡 상황별 선택 가이드

#### 👉 이럴 때는 REDIS를 선택하세요!
1. **극단적으로 빠른 응답 속도(1~2ms 이하)**가 최우선인 경우
2. 인증번호(3분), 이메일 인증 토큰, 일회용 세션 등 **정확한 TTL 만료 처리가 필수적인 임시 데이터**
3. 데이터의 양이 RAM 크기 내에서 충분히 수용 가능한 규모인 경우
4. 복잡한 검색 쿼리 없이 **Key-Value 또는 특정 자료구조(List, Set, ZSet) 연산** 위주인 경우
5. 일시적으로 유실되더라도 서비스 치명도가 낮거나 RDBMS에서 재적재 가능한 데이터

#### 👉 이럴 때는 일반 NoSQL(MongoDB/DynamoDB 등)을 선택하세요!
1. 임시 데이터이지만 **데이터의 양이 수백 GB ~ 수 TB 이상으로 매우 큰 경우** (RAM 비용 부담)
2. 임시 저장 데이터 내에서 **다양한 필드 조건 검색, 범위 조회, 정렬 등 복잡한 쿼리**가 필요한 경우
3. 임시 적재 후 배치 작업을 통해 분석/가공해야 하는 대용량 로그성 임시 데이터
4. 서버 장애 시에도 **데이터 유실이 절대 발생해서는 안 되는 높은 신뢰성**이 요구되는 경우

## 5. Java Spring 환경에서 Redis 사용하기 (코드 예시)

Spring Boot 환경에서는 `spring-boot-starter-data-redis` 의존성을 통해 Redis를 손쉽게 연동할 수 있습니다. 가장 많이 사용되는 **StringRedisTemplate**을 활용한 기본 연동 및 활용 예시를 살펴보겠습니다.

### 1) 의존성 추가 (build.gradle)

```groovy
dependencies {
    // Spring Data Redis (Lettuce 클라이언트 기본 내장)
    implementation 'org.springframework.boot:spring-boot-starter-data-redis'
}
```

### 2) 설정 (application.yml)

```yaml
spring:
  data:
    redis:
      host: localhost
      port: 6379
      # password: your_password (필요 시 설정)
      timeout: 3000ms
```

### 3) RedisConfig 설정 클래스

```java
package com.example.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.StringRedisSerializer;

@Configuration
public class RedisConfig {

    // 문자열 중심 Key-Value 처리에 최적화된 Template
    @Bean
    public StringRedisTemplate stringRedisTemplate(RedisConnectionFactory connectionFactory) {
        return new StringRedisTemplate(connectionFactory);
    }

    // 객체(Object) 직렬화 저장을 위한 Generic Template
    @Bean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory connectionFactory) {
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(connectionFactory);

        // Key는 String 직렬화, Value는 JSON 직렬화 적용
        template.setKeySerializer(new StringRedisSerializer());
        template.setValueSerializer(new GenericJackson2JsonRedisSerializer());
        template.setHashKeySerializer(new StringRedisSerializer());
        template.setHashValueSerializer(new GenericJackson2JsonRedisSerializer());

        return template;
    }
}
```

### 4) RedisService 실무 활용 예시 (Service 구현)

문자열 캐싱, 만료시간(TTL) 설정, 그리고 실시간 랭킹(ZSet)을 처리하는 서비스 코드입니다.

```java
package com.example.service;

import lombok.RequiredArgsConstructor;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.ZSetOperations;
import org.springframework.stereotype.Service;

import java.time.Duration;
import java.util.Set;

@Service
@RequiredArgsConstructor
public class RedisService {

    private final StringRedisTemplate redisTemplate;

    // 1. 단순 Key-Value 저장 (인증번호, 일회용 토큰 등 TTL 설정)
    public void setDataWithExpire(String key, String value, long durationMinutes) {
        redisTemplate.opsForValue().set(key, value, Duration.ofMinutes(durationMinutes));
    }

    // 2. Key로 데이터 조회
    public String getData(String key) {
        return redisTemplate.opsForValue().get(key);
    }

    // 3. 데이터 삭제
    public void deleteData(String key) {
        redisTemplate.delete(key);
    }

    // 4. 원자적 키 선점 (간단한 분산 락 / 중복 요청 방지)
    public boolean setIfAbsent(String key, String value, long durationSeconds) {
        Boolean isSuccess = redisTemplate.opsForValue()
                .setIfAbsent(key, value, Duration.ofSeconds(durationSeconds));
        return Boolean.TRUE.equals(isSuccess);
    }

    // 5. 실시간 랭킹 추가 (Sorted Set / ZSet 활용)
    public void addScoreToLeaderboard(String leaderboardKey, String userId, double score) {
        // 기존 점수에 score를 누적 가산
        redisTemplate.opsForZSet().incrementScore(leaderboardKey, userId, score);
    }

    // 6. 실시간 랭킹 Top N 조회 (점수 높은 순)
    public Set<ZSetOperations.TypedTuple<String>> getTopRankings(String leaderboardKey, int limit) {
        // 0위부터 (limit - 1)위까지 역순(내림차순) 조회
        return redisTemplate.opsForZSet().reverseRangeWithScores(leaderboardKey, 0, limit - 1);
    }
}
```

### 5) 선언적 캐시 어노테이션 (`@Cacheable`) 활용

반복적인 DB 조회를 줄이기 위해 Spring의 캐시 추상화 어노테이션을 사용할 수도 있습니다.

```java
@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository productRepository;

    // Cache-Aside 패턴: 캐시에 데이터가 있으면 반환하고, 없으면 DB 조회 후 Redis에 저장
    @Cacheable(value = "products", key = "#productId", cacheManager = "redisCacheManager")
    public ProductResponse getProduct(Long productId) {
        Product product = productRepository.findById(productId)
                .orElseThrow(() -> new IllegalArgumentException("상품이 존재하지 않습니다."));
        return ProductResponse.from(product);
    }

    // 데이터 변경 시 캐시 갱신/삭제
    @CacheEvict(value = "products", key = "#productId")
    public void updateProduct(Long productId, ProductUpdateRequest request) {
        // DB 상품 정보 업데이트 로직...
    }
}
```

## 6. 마치며 & 요약 정리

Redis는 단순한 캐시 서버를 넘어 현대 웹 아키텍처의 성능과 확장성을 책임지는 필수적인 인프라입니다.

- **REDIS란**: 초고속 In-Memory 기반 Key-Value 데이터 저장소
- **사용 이유**: RDBMS I/O 부하 절감, 빠른 응답 속도, 분산 환경 상태 동기화
- **실무 활용**: 캐싱, 분산 세션/토큰 관리, 실시간 랭킹(ZSet), 분산 락
- **임시 저장소 선택**: 
  - **초고속 응답 + 정확한 TTL + K-V 단순 구조** $\rightarrow$ **Redis**
  - **대용량 데이터 + 복잡한 쿼리 + 영속성 신뢰도** $\rightarrow$ **NoSQL**

서비스의 트래픽 특성과 데이터 수명 주기를 명확히 파악하여 적재적소에 Redis를 활용해보세요!
