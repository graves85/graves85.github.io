## 안녕하십니까! 😀

백엔드 개발 및 데이터베이스 운영 시 서비스 트래픽이 증가하고 데이터 양이 수백만~수천만 건으로 늘어나면, 가장 먼저 병목을 일으키는 지점이 바로 **느린 SQL 쿼리(Slow Query)**입니다.

단순히 `WHERE` 절에 컬럼을 추가하거나 무작정 인덱스를 건다고 해서 쿼리가 빨라지지 않습니다. 데이터베이스 옵티마이저(Optimizer)가 SQL을 내부적으로 어떻게 해석하고 처리하는지 알려주는 **실행 계획(Execution Plan)**을 읽고 분석할 수 있어야 근본적인 원인을 찾아 최적화할 수 있습니다.

오늘은 **실행 계획의 핵심 개념과 필수 체크 항목**, **주요 RDBMS(MySQL, PostgreSQL, Oracle)별 확인 방법**, **조인 및 인덱스 실행 계획 분석법**, **쿼리 속도에 큰 영향을 주는 SQL 작성 패턴(IN vs EXISTS, LIKE 등)**, 그리고 **인덱스 설계 시 필수 고려 요소**까지 한눈에 정리해보겠습니다! 💡

## 1. 실행 계획(Execution Plan)이란?

**실행 계획(Execution Plan)**이란 사용자가 작성한 SQL 문장을 처리하기 위해 데이터베이스의 두뇌인 **CBO(Cost-Based Optimizer, 비용 기반 옵티마이저)**가 생성한 **데이터 검색 및 처리 경로(경로 청사진)**를 의미합니다.

데이터베이스는 SQL을 수신하면 다음 과정을 거칩니다:
1. **구문 분석 (Parsing)**: SQL 문법 및 객체(테이블, 컬럼) 유효성 검증
2. **최적화 (Optimization)**: 통계 정보, 인덱스 현황 등을 바탕으로 가능한 여러 경로 중 가장 적은 비용(Cost)이 드는 최적의 실행 계획 수립
3. **실행 (Execution)**: 확정된 실행 계획에 따라 스토리지 엔진에서 데이터를 읽고 반환

### 📌 실행 계획에서 중점적으로 체크해야 할 핵심 항목 5가지

| 체크 항목 | 의미 및 점검 포인트 | 위험 신호 (Bad Case) |
| :--- | :--- | :--- |
| **1. 액세스 방식 (Access Type)** | 테이블/인덱스를 어떻게 읽는가? (Full Scan vs Index Range Scan) | 대용량 테이블에 대한 `TABLE ACCESS FULL`, `ALL` |
| **2. 예상 행 수 vs 실제 행 수 (Rows)** | 옵티마이저의 추정 행 수(Rows)와 실제 반환된 행 수(Actual Rows)의 차이 | 통계 정보 왜곡으로 인한 심각한 차이 $\rightarrow$ 잘못된 플랜 수립 |
| **3. 조인 방식 및 순서 (Join Type & Order)** | 어떤 조인 알고리즘을 사용하며, 드라이빙 테이블(Outer)이 적절한가? | 대용량 데이터 간 `Nested Loop Join` 또는 엉뚱한 테이블이 Driving |
| **4. 필터링 위치 및 효율 (Filter vs Access)** | 인덱스로 읽기 범위를 효과적으로 줄였는가, 테이블 접근 후 버렸는가? | 인덱스 스캔 후 불필요한 대량 필터링 발생 |
| **5. 부가 작업 (Extra Info)** | 정렬(Sort), 임시 테이블(Temporary), 파일 정렬 등이 발생하는가? | `Using filesort`, `Using temporary`, `Sort Join` 과다 |

## 2. 주요 RDBMS별 실행 계획 확인 및 실행 예시

각 RDBMS는 실행 계획을 확인하기 위한 전용 명령어와 상세 분석 도구를 제공합니다.

### 1) MySQL / MariaDB

MySQL에서는 `EXPLAIN` 또는 실제 쿼리를 실행하며 계측치를 측정하는 `EXPLAIN ANALYZE` (MySQL 8.0.18+)를 사용합니다.

```sql
-- 1. 기본 실행 계획 확인 (예상 계획)
EXPLAIN 
SELECT o.order_id, o.order_date, m.member_name 
FROM orders o 
JOIN members m ON o.member_id = m.member_id 
WHERE o.order_date >= '2026-01-01' AND m.status = 'ACTIVE';

-- 2. 실제 실행 시간 및 버퍼 소모량을 포함한 실행 분석 (권장)
EXPLAIN ANALYZE 
SELECT o.order_id, o.order_date, m.member_name 
FROM orders o 
JOIN members m ON o.member_id = m.member_id 
WHERE o.order_date >= '2026-01-01' AND m.status = 'ACTIVE';
```

#### 💡 MySQL 핵심 컬럼 해석
- `type`: `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` (우측으로 갈수록 성능 저하, `ALL`은 풀 테이블 스캔)
- `key`: 실제 선택된 인덱스 이름
- `rows`: 쿼리 수행을 위해 스캔할 것으로 예상되는 레코드 수
- `Extra`: `Using index`(커버링 인덱스, Best), `Using filesort`(디스크/메모리 정렬 발생, 주의), `Using temporary`(임시 테이블 생성, 주의)

---

### 2) PostgreSQL

PostgreSQL에서는 `EXPLAIN`에 `(ANALYZE, BUFFERS)` 옵션을 붙여 실제 실행 시간과 I/O 블록 읽기 수를 함께 확인하는 것이 정석입니다.

```sql
-- PostgreSQL 실행 계획 및 실제 I/O 버퍼 계측
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, COSTS)
SELECT o.order_id, o.order_date, m.name
FROM orders o
JOIN members m ON o.member_id = m.id
WHERE o.created_at >= '2026-01-01'
  AND m.tier = 'VIP';
```

#### 💡 PostgreSQL 주요 노드 해석
- `Seq Scan`: 테이블 순차 전체 스캔 (대용량 테이블 시 주의)
- `Index Scan` / `Index Only Scan`: 인덱스를 통한 조회 (`Index Only Scan`은 커버링 인덱스)
- `Bitmap Index Scan` $\rightarrow$ `Bitmap Heap Scan`: 인덱스를 통해 조건에 맞는 페이지 비트맵을 생성한 후 테이블 일괄 접근 (중간 규모 데이터에 효과적)
- `Buffers: shared hit=..., read=...`: `hit`은 메모리(버퍼 캐시) 접근, `read`는 디스크 I/O 발생을 의미

---

### 3) Oracle

오라클에서는 `AUTOTRACE`를 켜거나 `DBMS_XPLAN` 패키지를 통해 실행 계획과 실제 런타임 통계(`GATHER_PLAN_STATISTICS`)를 조회합니다.

```sql
-- 1. 통계 수집 힌트를 포함한 쿼리 실행
SELECT /*+ GATHER_PLAN_STATISTICS */
       o.order_id, o.order_date, m.member_name
FROM orders o, members m
WHERE o.member_id = m.member_id
  AND o.order_date >= TO_DATE('2026-01-01', 'YYYY-MM-DD')
  AND m.status = 'ACTIVE';

-- 2. 가장 최근 실행한 쿼리의 실제 런타임 실행 계획 확인
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));
```

#### 💡 Oracle 실행 계획 핵심 컬럼 해석
- `A-Rows` (Actual Rows) vs `E-Rows` (Estimated Rows): 실제 행과 예상 행의 일치 여부 확인 (오차가 크면 `DBMS_STATS`로 통계 갱신 필요)
- `Buffers` (CR Reads): 쿼리가 읽은 총 메모리 블록 수 (이 값이 적을수록 효율적인 쿼리)
- `Reads`: 물리적 디스크 I/O 블록 수

## 3. 조인(Join) 실행 계획, 어떤 걸 중점적으로 보아야 할까?

조인 쿼리 튜닝 시 실행 계획에서 반드시 검토해야 하는 3가지 요소는 **조인 기법**, **드라이빙 테이블(Driving Table)**, **조인 버퍼 및 조인 컬럼 인덱스**입니다.

```
[조인의 기본 원리]
선행(Driving) 테이블 ──(조건 만족 행 1건씩 추출)──► 후행(Driven/Inner) 테이블 인덱스 탐색
```

### 1) 주요 조인 방식(알고리즘)의 이해 및 점검

```
1. Nested Loop Join (NL 조인)
   - 중첩 반복문 형태로 외부(선행) 테이블의 각 행마다 내부(후행) 테이블의 인덱스를 탐색
   - [최적 상황]: 선행 테이블의 결과 집합이 소량(수천 건 이하)이고, 후행 테이블의 조인 키에 인덱스가 있는 경우 (OLTP 웹 환경 표준)

2. Hash Join (해시 조인)
   - 선행(작은) 테이블로 메모리에 해시 테이블(Build)을 만든 후 후행(대용량) 테이블을 읽으며 매칭(Probe)
   - [최적 상황]: 대용량 테이블 간의 조인이거나 조인 조건 컬럼에 적절한 인덱스가 없을 때 (배치/DW/집계에 유리)

3. Sort Merge Join (정렬 병합 조인)
   - 양쪽 테이블을 조인 키 기준으로 각각 정렬한 후 병합
   - [최적 상황]: 조인 조건이 범위 비교(`<`, `>`, `BETWEEN`)이거나 이미 양쪽 데이터가 인덱스로 정렬되어 있는 경우
```

### 2) 조인 튜닝 시 핵심 점검 체크리스트

1. **드라이빙 테이블(선행 테이블)이 충분히 작은가?**
   - 필터 조건(`WHERE`)을 거쳐 **최종적으로 걸러진 데이터 건수가 더 적은 테이블**이 선행 테이블로 선택되어야 후행 테이블 탐색 횟수가 최소화됩니다.
2. **후행 테이블(드리븐 테이블)의 조인 컬럼에 인덱스가 있는가?**
   - NL 조인 시 후행 테이블 조인 컬럼에 인덱스가 없으면 선행 테이블 행 수만큼 후행 테이블을 Full Table Scan하게 되어 치명적인 성능 저하가 발생합니다.
3. **불필요한 해시 조인(Hash Join)이나 풀 스캔이 발생하지 않는가?**
   - 실시간 OLTP 웹 쿼리에서 메모리(PGA/Work Mem)를 많이 소모하는 해시 조인이 빈번하다면 인덱스 누락 여부를 확인해야 합니다.

## 4. 인덱스(Index) 실행 계획, 어떤 걸 중점적으로 보아야 할까?

인덱스가 걸려 있다고 해서 항상 최적으로 동작하는 것은 아닙니다. 실행 계획에서 **인덱스 스캔 방식**과 **액세스/필터 조건의 분리 여부**를 확인해야 합니다.

### 1) 인덱스 스캔 유형별 효율성 비교

```
[효율성 높음] ──────────────────────────────────────────► [효율성 낮음]
Index Unique Scan  >  Index Range Scan  >  Index Full Scan  >  Index Fast Full Scan  >  Table Full Scan
```

- **Index Unique Scan (PK / Unique EQ 조회)**: 단 1건의 데이터를 수직적 탐색(Vertical Search)으로 즉시 찾음.
- **Index Range Scan (범위/선두컬럼 조건 조회)**: 인덱스 루트 $\rightarrow$ 브랜치 $\rightarrow$ 리프 블록을 거쳐 필요한 구간만 수평 스캔. 가장 일반적이고 권장되는 방식.
- **Index Full Scan (인덱스 전체 스캔)**: 테이블 풀 스캔보다는 블록 수가 작지만, 인덱스 리프 노드 전체를 스캔하므로 대용량에서는 튜닝 대상.
- **Index Fast Full Scan (멀티 블록 I/O 전체 인덱스 스캔)**: 순서와 무관하게 인덱스 세그먼트 블록을 병렬/멀티블록으로 읽음.

### 2) Index Access Condition vs Index Filter Condition 구분

인덱스 성능에서 가장 중요한 개념 중 하나는 **액세스 조건**과 **필터 조건**의 차이입니다.

- **인덱스 액세스 조건 (Access Condition)**: 인덱스 리프 블록의 시작 위치와 끝 위치를 결정하는 조건입니다. (스캔 범위를 물리적으로 줄여줌 $\rightarrow$ 속도 대폭 향상)
- **인덱스 필터 조건 (Filter Condition)**: 스캔 범위는 줄이지 못하고, 인덱스를 읽으면서 조건을 만족하는지 단순 검사 후 버리는 조건입니다. (스캔 범위 감소 효과 없음)

> 💡 **튜닝 팁**: 복합 인덱스 설계 시 선두 컬럼이 `BETWEEN`, `LIKE 'ABC%'`, `>`, `<` 같은 범위 조건이면 그 뒤에 오는 컬럼들은 액세스 조건이 아닌 **단순 필터 조건**으로 동작하게 되므로 컬럼 순서 배치에 유의해야 합니다.

## 5. 쿼리 속도에 직접적인 영향을 주는 SQL 문법 및 패턴 튜닝

동일한 결과를 반환하더라도 문법 작성 방식에 따라 옵티마이저가 생성하는 실행 계획과 성능이 천차만별입니다.

### 1) `IN` vs `EXISTS` (서브쿼리 최적화)

과거 버전에서는 `IN` 서브쿼리가 비효율적이었으나, 최신 옵티마이저는 세미 조인(Semi-Join)으로 최적화합니다. 하지만 서브쿼리의 특성에 따라 유리한 문법이 다릅니다.

#### ❌ 주의해야 할 패턴 (IN 서브쿼리)
```sql
-- 서브쿼리 결과 건수가 수십만 건 이상으로 매우 많을 때
SELECT * 
FROM orders o 
WHERE o.member_id IN (
    SELECT member_id 
    FROM members 
    WHERE created_at >= '2020-01-01' -- 수백만 건 반환
);
```

####  최적화 패턴 (EXISTS 활용)
```sql
-- 메인 테이블(orders)의 특정 조건에 대해 존재 여부만 1건 확인하고 즉시 멈춤 (Early-Exit)
SELECT * 
FROM orders o 
WHERE EXISTS (
    SELECT 1 
    FROM members m 
    WHERE m.member_id = o.member_id 
      AND m.status = 'ACTIVE'
);
```

> 📌 **선택 기준**:
> - **메인 쿼리 결과가 적고 서브쿼리 테이블이 크다면 $\rightarrow$ `EXISTS`** (서브쿼리 인덱스를 타고 1건만 확인 후 즉시 리턴)
> - **서브쿼리 결과가 고정된 상수 리스트이거나 극소수라면 $\rightarrow$ `IN`**

---

### 2) `LIKE` 전방 일치 vs 후방 일치

```sql
-- ❌ 나쁜 예: 인덱스 Range Scan 불가 (Table Full Scan 유발)
SELECT * FROM members WHERE phone_number LIKE '%1234';
SELECT * FROM members WHERE email LIKE '%@gmail.com';

--  좋은 예: 인덱스 Range Scan 정상 활용
SELECT * FROM members WHERE member_name LIKE '김철수%';
```

- 인덱스는 B-Tree 정렬 구조이므로 `%`가 앞에 오는 후방 일치(`%ABC`)나 양방향 일치(`%ABC%`)는 인덱스 시작점을 찾을 수 없어 **Full Scan**을 타게 됩니다.
- 뒷자리 검색이 잦다면 컬럼을 역순으로 저장하는 `REVERSE` 컬럼/인덱스를 도입하거나 전문 검색(Full-text Index)을 고려해야 합니다.

### 3) WHERE 조건절 컬럼 가공 금지 (인덱스 무력화 방지)

조건절의 좌변(컬럼)을 함수나 연산으로 가공하면 B-Tree 인덱스를 탈 수 없습니다.

```sql
-- ❌ 나쁜 예: 컬럼을 가공하여 인덱스 사용 불가 (Full Table Scan)
SELECT * FROM orders WHERE SUBSTR(order_no, 1, 4) = '2026';
SELECT * FROM orders WHERE DATE_FORMAT(order_date, '%Y-%m-%d') = '2026-08-25';
SELECT * FROM products WHERE price * 0.9 <= 10000;

--  좋은 예: 컬럼은 그대로 두고 우변(상수/값)을 가공
SELECT * FROM orders WHERE order_no LIKE '2026%';
SELECT * FROM orders WHERE order_date >= '2026-08-25 00:00:00' 
                       AND order_date < '2026-08-26 00:00:00';
SELECT * FROM products WHERE price <= 10000 / 0.9;
```

---

### 4) 암묵적 형변환(Implicit Type Conversion) 방지

컬럼의 데이터 타입과 비교 값의 데이터 타입이 다르면 DB가 내부적으로 함수를 씌워 컬럼을 형변환하므로 인덱스가 동작하지 않습니다.

```sql
-- varchar_column이 VARCHAR(20) 문자형인 경우
-- ❌ 나쁜 예: 숫자로 비교 시 내부적으로 CAST(varchar_column AS SIGNED) 처리됨
SELECT * FROM users WHERE user_id = 100542;

--  좋은 예: 문자형 리터럴로 정확히 매칭
SELECT * FROM users WHERE user_id = '100542';
```

---

### 5) `COUNT(*)` vs `COUNT(column)` 및 페이징 최적화

- `COUNT(*)`는 NULL을 포함한 전체 행 수를 집계하므로 옵티마이저가 가장 가벼운 보조 인덱스를 골라 스캔합니다.
- `COUNT(column)`은 해당 컬럼의 NULL 체크를 위해 불필요한 I/O가 늘어날 수 있습니다.
- 대량 데이터의 `OFFSET, LIMIT` 페이징은 **No-Offset 방식(Covering Index 활용 또는 `WHERE id > last_seen_id`)**으로 튜닝해야 뒤쪽 페이지 조회 시 성능 저하를 막을 수 있습니다.

## 6. 인덱스(Index) 생성 시 필수적으로 확인해야 할 핵심 요소

인덱스는 무조건 많다고 좋은 것이 아닙니다. 인덱스가 늘어날수록 `INSERT`, `UPDATE`, `DELETE` 성능이 급격히 저하되고 디스크 용량을 낭비하게 됩니다.

인덱스를 설계하고 생성할 때는 다음 **5가지 필수 요소**를 철저히 검토해야 합니다.

```
[인덱스 설계 5대 체크포인트]
1. 카디널리티 (선택도) ──► 고유값(Distinct)이 많고 선택도가 5~15% 이내인가?
2. 복합 인덱스 컬럼 순서 ─► [1] = (점조건)  ──►  [2] 범위(<, >, LIKE) 순으로 배치했는가?
3. 커버링 인덱스 여부 ────► 테이블 랜덤 액세스(I/O)를 아예 없앨 수 있는가?
4. 쓰기(DML) 부하 트레이드오프 ─► 불필요한 중복/유사 인덱스가 난립하지 않았는가?
5. 데이터 분포도 & 통계 ──► 정기적인 통계 정보 갱신(Analyze)이 이루어지는가?
```

### 1) 카디널리티(Cardinality)와 선택도(Selectivity)
- **카디널리티**: 해당 컬럼의 고유한 값(Distinct Value)의 개수
- **선택도(Selectivity)**: `(선택된 행 수 / 전체 행 수) * 100`
- 성별(`남/여`), 사용여부(`Y/N`)처럼 카디널리티가 낮고 선택도가 50%에 달하는 컬럼은 인덱스를 걸어도 풀 스캔보다 느릴 수 있습니다. **선택도가 5~15% 이내로 낮은(변별력이 높은) 컬럼**에 인덱스를 생성해야 합니다.

### 2) 복합 인덱스(Composite Index)의 컬럼 순서 결정 원칙
복합 인덱스는 컬럼 순서가 성능을 좌우합니다.
1. **제 1원칙**: `WHERE` 절에서 항상 동등 비교(`=`)로 사용되는 컬럼을 가장 앞(선두)에 배치합니다.
2. **제 2원칙**: 범위 조건(`<`, `>`, `BETWEEN`, `LIKE 'A%'`)으로 사용되는 컬럼은 동등 조건 컬럼 뒤에 배치합니다.
3. **제 3원칙**: `ORDER BY`, `GROUP BY`에 사용되는 컬럼 순서와 일치시켜 추가 정렬 작업(`filesort`, `Temp table`)을 제거합니다.

### 3) 커버링 인덱스(Covering Index) 활용
- 쿼리가 필요로 하는 모든 컬럼(`SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`)을 인덱스 자체에 포함시키는 기법입니다.
- 인덱스 리프 노드만 읽고 **테이블 데이터 블록으로의 랜덤 I/O(랜덤 액세스)를 완전히 생략**하므로 가장 극적인 속도 개선을 이끌어낼 수 있습니다. (MySQL 실행 계획 `Extra: Using index`)

### 4) 중복 및 미사용 인덱스 정리
- `(A, B)` 복합 인덱스가 이미 존재한다면, 단일 컬럼 `(A)` 인덱스는 중복이므로 제거해야 합니다.
- 정기적으로 미사용 인덱스(`sys.schema_unused_indexes` 등)를 모니터링하여 삭제함으로써 DML 트랜잭션 성능을 보장해야 합니다.

### 5) 최신 데이터베이스 통계 정보(Statistics) 유지
- CBO 옵티마이저는 데이터 분포도 통계를 기반으로 비용을 계산합니다.
- 대량 배치 적재나 데이터 대규모 삭제 후에는 반드시 `ANALYZE TABLE` (MySQL), `VACUUM ANALYZE` (PostgreSQL), `DBMS_STATS.GATHER_TABLE_STATS` (Oracle)를 실행하여 통계 정보를 최신화해야 옵티마이저가 엉뚱한 인덱스를 타지 않습니다.

## 7. 마치며 & 요약 정리

SQL 튜닝은 막연한 감이나 추측으로 하는 것이 아니라, **옵티마이저의 실행 계획을 눈으로 확인하고 I/O 비용을 줄여나가는 과학적인 과정**입니다.

- **실행 계획 확인**: `EXPLAIN ANALYZE` 등을 통해 예상 계획뿐 아니라 실제 소요 시간과 I/O 블록 수를 확인하기
- **조인 최적화**: 건수가 적은 테이블을 선행(Driving)으로 두고, 후행 테이블 조인 컬럼 인덱스 확인하기
- **인덱스 스캔**: 단순 필터가 아닌 스캔 범위를 줄이는 **액세스 조건**으로 유도하고, 가능하면 **커버링 인덱스** 적용하기
- **안티패턴 피하기**: 조건절 컬럼 가공 금지, 암묵적 형변환 방지, `%ABC` 전방 와일드카드 금지
- **인덱스 설계**: 고 카디널리티 컬럼 우선, `[동등 조건(=) $\rightarrow$ 범위 조건]` 순으로 복합 인덱스 구성하기
