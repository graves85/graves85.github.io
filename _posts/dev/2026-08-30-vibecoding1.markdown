## 안녕하십니까! 😀

AI 코딩 도구가 보편화되면서 **"감으로 맡기고 결과만 받는" 바이브 코딩(Vibe Coding)** 이 빠르게 퍼지고 있습니다. 속도는 분명 매력적이지만, 요구사항이 흐릿하거나 검증이 없으면 **그럴듯한 코드가 빠르게, 그리고 대량으로** 쌓이기 쉽습니다.

오늘은 바이브 코딩을 "운에 맡기는 작업"이 아니라 **설계 → 규칙 → 구현 → 검증** 루프로 다루는 실전 방법을 정리합니다.

- 개발 전 요구사항 설계 및 Phase 설정
- 품격 있는 컨벤션으로 질의하기
- 쉽게 끝난 개발을 체계적으로 검증하기
- **RAC(Rules · Agents · Context)** 로 환경 설정 및 필수 정보 주기
- 그 외 주의할 점

---

## 1. 개발 전 요구사항 설계 및 Phase 설정하기

바이브 코딩의 성패는 **첫 프롬프트 이전**에 거의 결정됩니다. AI는 "무엇을 만들지"보다 **"지금 어디까지 할지"** 가 분명할 때 훨씬 안정적으로 움직입니다.

### 📌 요구사항을 먼저 문장으로 고정하라

구현을 시키기 전에 아래 항목을 짧게라도 적어 둡니다.

```
[Goal]     사용자가 무엇을 할 수 있어야 하는가?
[In/Out]   입력은 무엇이고, 성공/실패 결과는 무엇인가?
[Scope]    이번 작업에 포함 / 제외할 것
[Constraint] 기술 스택, 성능, 보안, 하위 호환
[Done]     무엇이 확인되면 "완료"인가?
```

### 💡 Phase로 쪼개면 환각과 과잉 구현이 줄어든다

한 번에 "전체 기능 만들어줘"보다, **검증 가능한 단계**로 나눕니다.

```
Phase 0  Discovery   현재 코드/도메인 파악, 영향 범위 정리 (구현 X)
Phase 1  Skeleton    인터페이스·디렉터리·빈 구현·테스트 뼈대
Phase 2  Core Path   Happy Path만 동작하게
Phase 3  Edge Cases  예외, 권한, 동시성, 롤백
Phase 4  Hardening   로깅, 관측, 성능, 보안, 문서
```

### 💻 Phase 지시 프롬프트 예시

```text
지금은 Phase 1만 진행한다.
- 목표: 주문 취소 API의 컨트롤러/서비스 시그니처와 실패 코드 enum만 추가
- 금지: DB 마이그레이션, UI, 외부 연동 구현
- 완료 조건: 컴파일 가능, 빈 구현에 TODO 주석, 관련 테스트 스켈레톤 존재
- 작업 후: 변경 파일 목록과 Phase 2에서 할 일을 3줄로 보고
```

**한 Phase = 한 목표 + 한 완료 조건 + 한 검증** 이 되면, AI가 옆길로 새는 빈도가 눈에 띄게 줄어듭니다.

## 2. 품격 있게 컨벤션을 만들어서 질의하기

바이브 코딩에서 "품격"은 말투가 아니라 **의사결정의 일관성**입니다. 팀 컨벤션을 프롬프트에 녹이면, 결과물이 사람 손 코드와 같은 결을 유지합니다.

### 📌 좋은 질의의 뼈대: Role → Context → Constraint → Output

```text
[Role]       당신은 이 저장소의 시니어 백엔드 개발자다.
[Context]    관련 파일: OrderService.java, CancelOrderUseCase.java
[Constraint] 기존 패키지 구조·네이밍·예외 계층을 유지한다. 새 프레임워크 도입 금지.
[Task]       주문 취소 유스케이스의 도메인 규칙을 구현한다.
[Output]     1) 변경 요약 2) 코드 3) 테스트 방법 4) 남은 리스크
```

### 💡 컨벤션을 "취향"이 아니라 "계약"으로 적기

| 영역 | 예시 규칙 |
|------|-----------|
| 네이밍 | `*Service`는 애플리케이션, `*DomainService`는 도메인 규칙 |
| 에러 | 비즈니스 예외는 `BusinessException` 하위만 사용 |
| API | 응답은 `ApiResponse<T>`, 에러코드는 enum |
| 테스트 | Given-When-Then, 외부 I/O는 테스트 더블 |
| 변경 범위 | 요청하지 않은 리팩터링/포맷 대청소 금지 |

### 💻 품격 있는(명확한) vs 흐릿한 질의

```text
❌ "주문 취소 예쁘게 만들어줘"

⭕ "기존 CancelOrderUseCase 패턴을 따라 주문 취소를 구현해줘.
   - 이미 취소된 주문은 ALREADY_CANCELED
   - 결제 완료 후 취소용 외부 API 호출은 PaymentGateway.port 경유
   - 트랜잭션은 UseCase 계층에서만 연다
   - 단위 테스트 3개(성공/이미취소/결제실패) 추가
   - 관련 없는 파일은 수정하지 말 것"
```

컨벤션이 문서화되어 있으면, 매 질의마다 같은 말을 반복하지 않아도 됩니다. 그 문서가 바로 다음 장의 **Rules** 입니다.

## 3. 쉽게 완료된 개발을 체계적으로 검증하기

바이브 코딩의 함정은 **"동작하는 것처럼 보이는 것"** 을 완료로 착각하는 일입니다. AI가 "완료했습니다"라고 해도, 사람은 **증빙**을 받아야 합니다.

### 📌 최소 검증 피라미드

```
        ┌─────────────┐
        │ 수동 스모크  │  핵심 화면/API 1~2경로
        ├─────────────┤
        │ 통합/계약    │  API·DB·메시지 경계
        ├─────────────┤
        │ 단위 테스트  │  도메인 규칙·분기
        ├─────────────┤
        │ 정적 점검    │  빌드, 린트, 타입, 시크릿 스캔
        └─────────────┘
```

### 💡 "완료 보고"를 강제하는 체크리스트

AI에게 구현과 함께 아래를 반드시 제출하게 합니다.

1. **변경 의도**: 무엇을 위해 어떤 파일을 바꿨는지
2. **검증 명령**: 로컬에서 재현 가능한 명령어 (`./gradlew test`, `npm test` 등)
3. **통과/실패 근거**: 테스트명, 응답 예시, 스크린샷/로그 요약
4. **미검증 구간**: 아직 안 돌린 것, 가정한 것
5. **롤백 포인트**: 문제 시 되돌릴 커밋/범위

### 💻 검증 요청 프롬프트 예시

```text
구현은 끝났다고 가정하지 말고, 검증 모드로 전환해라.
1) 방금 변경과 관련된 테스트만 실행하는 명령을 제시
2) 성공 기준과 실패 시 의심 지점을 적어라
3) 보안/동시성/데이터 정합성 관점에서 리뷰 코멘트 5개
4) "확인하지 않은 것"을 명시적으로 목록화
코드 수정은 내가 요청하기 전까지 하지 말 것.
```

**쉽게 끝난 작업일수록** 회귀·권한·경계값·멱등성처럼 "안 깨져 보이는" 영역을 우선 의하세요. 속도의 이득은 검증 루프가 짧을 때 진짜로 남습니다.

## 4. RAC을 이용한 바이브 코딩 설정 및 필수 정보 주기

도구만 켜 두고 채팅만 하는 것은 설정이 아닙니다. 효과적인 바이브 코딩은 **RAC** 삼각 구조로 환경을 고정하는 것에서 시작합니다.

```
        Rules (규칙)
           /\
          /  \
         /    \
 Agents <------> Context
 (역할/절차)     (필수 정보)
```

### 📌 R — Rules: AI가 매번 지켜야 할 계약

프로젝트 루트의 규칙 파일(예: `.cursor/rules`, `AGENTS.md`, `CLAUDE.md`)에 **짧고 강제력 있는** 문장으로 적습니다.

```markdown
# Project Rules (요약 예시)
- 기존 계층/네이밍을 존중한다. 요청 없는 대규모 리팩터링 금지.
- 시크릿·실서버 URL·프로덕션 자격 증명을 코드/로그에 넣지 않는다.
- 테스트 없는 비즈니스 로직 변경은 WIP로 표시한다.
- 응답 형식: 변경 요약 → 코드 → 검증 방법 → 리스크.
```

Rules는 "에세이"가 아니라 **위반 시 바로 지적할 수 있는 조항**이어야 합니다.

### 📌 A — Agents: 역할과 절차를 분리한다

한 에이전트에게 설계·구현·검증·문서화를 전부 맡기면 컨텍스트가 오염됩니다. 역할별로 모드를 나누세요.

| Agent 모드 | 하는 일 | 하지 않는 일 |
|------------|---------|--------------|
| Planner | Phase/영향범위/리스크 정리 | 대규모 코드 수정 |
| Implementer | 지정 Phase만 구현 | 범위 밖 리팩터링 |
| Reviewer | 결함·보안·누락 검증 | "일단 고쳐서" 임의 수정 |
| Docs | CHANGELOG/사용법 정리 | 동작 변경 |

### 📌 C — Context: 필수 정보를 미리 주입한다

AI가 매번 추측하게 두지 말고, **자주 쓰는 진실(Source of Truth)** 을 컨텍스트로 제공합니다.

- 아키텍처 한 장 요약 (모듈 경계, 의존 방향)
- API/이벤트 계약, 에러 코드 표
- 로컬 실행·테스트 명령
- "절대 건드리면 안 되는" 영역
- 도메인 용어 사전 (예: *취소* vs *환불*)

필요하면 문서/위키를 검색해 붙이는 **RAG(Retrieval-Augmented Generation)** 도 Context 계층을 보강하는 수단입니다.  
다만 바이브 코딩 설정에서는 **항상 켜 두는 Rules/Agents** 와 **이번에 필요한 Context** 를 구분하는 것이 중요합니다.

### 💻 RAC 세팅 체크리스트

```
[ ] Rules에 스택·금지사항·출력 포맷이 있다
[ ] Phase/리뷰용 Agent(또는 모드) 전환 문구가 준비되어 있다
[ ] README 또는 docs에 실행/테스트/배포 정보가 있다
[ ] 이번 작업 관련 파일·스펙만 Context로 첨부한다 (전체 덤프 금지)
[ ] 민감정보는 규칙으로 차단되어 있다
```

**필수 정보를 주는 기준**은 "있으면 추측이 사라지는가?" 입니다. 추측이 남는 지점은 다음 Phase의 입력으로 남기세요.

## 5. 그 외 바이브 코딩을 할 때 주의해야 할 점

### 🔑 1) 속도 ≠ 진척
생성된 줄 수보다 **통과한 검증**과 **닫힌 리스크**로 진척을 측정하세요.

### 🔑 2) 컨텍스트 과식은 독이다
관련 없는 파일·장문 로그·전체 레포 덤프는 모델을 산만하게 만듭니다. Phase에 필요한 최소 컨텍스트만 넣습니다.

### 🔑 3) 보안·비밀은 사람 관할
API 키, 토큰, 고객 데이터, 프로덕션 접속 정보는 채팅/규칙 예시에 넣지 마세요. AI가 "임시로" 하드코딩해도 즉시 거부합니다.

### 🔑 4) 환각한 의존성/API를 경계하라
존재하지 않는 라이브러리, 잘못된 옵션, 예전 메이저 버전 API를 자신 있게 쓸 수 있습니다. **공식 문서나 로컬 코드로 한 번 더 확인**하세요.

### 🔑 5) 커밋 원자성을 지켜라
AI가 한 번에 바꾼  Bundled 변경을 그대로 커밋하면 리뷰와 롤백이 어려워집니다. Phase·의도 단위로 나누어 커밋합니다.

### 🔑 6) "왜"를 물어보는 습관
결과가 맞아 보여도 `이 설계를 선택한 이유와 대안 1개`를 물어보면, 숨은 가정을 일찍 드러낼 수 있습니다.

### 🔑 7) 소유권은 개발자에게 있다
바이브 코딩은 가속도 페달입니다. **머지 버튼과 장애 책임은 사람**에게 있습니다.

## 6. 마치며 & 요약 정리

바이브 코딩을 효과적으로 쓰려면, AI에게 "느낌"을 맡기는 것이 아니라 **작업의 형식을 설계**해야 합니다.

- **요구사항 + Phase**: 한 번에 전부 시키지 말고, 검증 가능한 단위로 자른다
- **컨벤션 질의**: Role/Context/Constraint/Output으로 품격(=일관성)을 만든다
- **체계적 검증**: 완료 선언이 아니라 명령·테스트·미검증 목록으로 증명한다
- **RAC 설정**: Rules로 계약을, Agents로 역할을, Context로 필수 정보를 고정한다
- **주의점**: 과잉 컨텍스트, 비밀 유출, 환각 API, 비원자적 커밋을 경계한다

결국 좋은 바이브 코딩은 **"AI가 잘 코딩하게 만드는 일"** 이 아니라, **"사람이 잘 감독할 수 있는 루프를 만드는 일"** 에 가깝습니다.

긴 글 읽어주셔서 감사합니다. 궁금한 점이나 의견은 언제든 편하게 댓글 남겨주세요! 😊
