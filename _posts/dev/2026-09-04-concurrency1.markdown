## 안녕하십니까! 😀

서버가 수천·수만 개의 요청을 동시에 받아도 버틸 수 있는 비결은 무엇일까요?  
답은 종종 **"스레드를 더 늘리는 것"**이 아니라, **"스레드처럼 보이지만 훨씬 가벼운 실행 단위"**를 쓰는 것입니다.

오늘은 그 대표 주자 세 가지를 나란히 놓고 정리합니다.

- **Go 고루틴(Goroutine)**
- **Kotlin(및 일반적 의미의) 코루틴(Coroutine)**
- **Java 가상 스레드(Virtual Thread, Project Loom)**

각 모델이 **일을 어떻게 처리하는지(비유 포함)**, **무엇이 같고 다른지**, **언제 어떤 제약이 있고 어디에 맞는지**까지 한 번에 훑어보겠습니다! 🚀

## 0. 먼저 공통 배경: OS 스레드가 비싼 이유

전통적인 **OS 스레드(Platform Thread)** 는 운영체제가 스케줄링합니다.  
스택 메모리가 크고(대개 MB 단위), 생성·전환 비용이 커서 **"요청당 스레드 하나"** 모델은 I/O가 많은 서버에서 금방 한계에 부딪힙니다.

가벼운 동시성 모델 세 가지는 공통적으로 이런 목표를 가집니다.

> **동기식처럼 읽히는 코드**로, **비동기·논블로킹에 가까운 효율**을 내고 싶다.

다만 **누가 스케줄링하느냐**, **어디서 멈추고 재개하느냐**, **블로킹을 어떻게 다루느냐**에서 갈라집니다.

## 1. 각 모델의 처리 방식 (비유로 이해하기)

### 📌 비유 한 줄 요약

| 모델 | 한 줄 비유 |
|------|------------|
| **고루틴** | 공장에 **아주 얇은 작업자**를 수만 명 두고, Go 런타임이 소수 기계(OS 스레드)에 배정 |
| **코루틴** | 요리사가 **레시피의 대기 구간(suspend)** 에서 손을 놓고 다른 요리를 이어서 함 |
| **가상 스레드** | 기존 **"직원(스레드) 한 명 = 일 하나"** 문법을 유지하되, 직원은 **초경량 아바타**로 바뀜 |

---

### 🟢 Go 고루틴 — "런타임이 키우는 초경량 작업자"

고루틴은 Go 런타임이 관리하는 **경량 스레드**입니다.  
수천·수백만 개를 만들어도 OS 스레드처럼 무겁지 않고, **M:N 스케줄링**(많은 고루틴 M개를 적은 OS 스레드 N개에 매핑)으로 돕니다.

#### 🏭 비유: 택배 허브의 임시 알바

- **OS 스레드** = 고정된 컨베이어 라인(비싸고 적음)
- **고루틴** = 그때그때 뽑는 알바(싸고 많음)
- **Go 스케줄러** = 배차 담당자  
  알바가 대기(채널/`select`/네트워크 I/O)에 들어가면, 그 라인을 다른 알바에게 넘깁니다.

```go
func main() {
    ch := make(chan string)

    go func() {
        // 이 블록이 고루틴 — 함수 앞에 go만 붙이면 끝
        ch <- fetchUser()
    }()

    fmt.Println(<-ch) // 채널로 결과를 주고받음
}
```

#### 처리의 핵심
- **선점(preemption)** 에 가깝게 동작할 수 있어, CPU를 오래 붙잡는 고루틴도 런타임이 개입하기 쉽습니다.
- 통신은 공유 메모리보다 **채널(CSP 스타일)** 을 권장합니다.
- I/O·채널 대기 시 해당 고루틴은 파킹되고, OS 스레드는 다른 고루틴을 돌립니다.

---

### 🟣 코루틴 — "협력적으로 양보하는 중단 가능한 함수"

코루틴(특히 Kotlin Coroutines)은 **"스레드의 대체품"이라기보다**, **중단(suspend)과 재개(resume)가 가능한 계산 단위**에 가깝습니다.  
실제 실행은 보통 **소수의 스레드 풀(Dispatcher)** 위에서 돌아가고, `suspend` 지점에서 **스레드를 점유하지 않은 채** 기다릴 수 있습니다.

#### 👨‍🍳 비유: 한 명의 셰프, 여러 접시의 레시피

- **스레드** = 주방의 실제 쉐프(몸)
- **코루틴** = 접시별 레시피 카드
- **suspend / await** = "오븐 울릴 때까지 이 접시는 내려놓고, 다른 접시를 손질한다"

쉐프는 한 명(또는 소수)인데도, 대기 구간을 양보하기 때문에 **동시에 진행 중인 요리(코루틴)** 는 수백·수천 개가 될 수 있습니다.

```kotlin
suspend fun loadProfile(userId: String): Profile = coroutineScope {
    val user = async { userApi.get(userId) }      // 논블로킹 대기 가능
    val orders = async { orderApi.list(userId) }
    Profile(user.await(), orders.await())
}
```

#### 처리의 핵심
- **협력적(cooperative)**: `suspend` 지점에서 양보합니다. 무한 루프처럼 suspend 없는 CPU 작업은 스레드를 막을 수 있습니다.
- Kotlin은 **Structured Concurrency**(부모-자식 Job 계층)로 취소·예외·수명을 묶습니다.
- "코루틴"이라는 말은 언어마다 다릅니다.  
  - Kotlin/JS/Python 등은 **async/await·제너레이터형 중단점** 중심  
  - Go 고루틴은 이름에 coroutine이 없어도 **경량 동시성** 계열로 자주 비교됩니다.

---

### 🟠 Java 가상 스레드 — "문법은 스레드, 속은 경량 캐리어"

Java 21+의 **Virtual Thread**는 "스레드 API를 그대로" 쓰면서, 구현체만 가볍게 바꿉니다.  
가상 스레드는 **캐리어(carrier)인 소수의 플랫폼 스레드** 위에서 스케줄링되고, 블로킹 I/O를 만나면 JVM이 가상 스레드를 언마운트해 **캐리어를 다른 가상 스레드에 빌려줍니다**.

#### 🎭 비유: 창구는 10개, 번호표는 10만 장

- **플랫폼 스레드** = 은행 창구 직원(소수, 비쌈)
- **가상 스레드** = 번호표 든 손님(많음, 쌈)
- 손님이 서류 발급을 기다리며 자리를 비우면(블로킹 I/O), 창구 직원은 **다음 손님**을 받습니다.
- 개발자 코드는 여전히 `Thread.start()` / `ExecutorService` 감성이라 **기존 동기 코드 이식이 쉽습니다.**

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i ->
        executor.submit(() -> {
            // 동기식으로 보여도, 블로킹 I/O 구간에서 캐리어를 양보
            return httpClient.send(request, BodyHandlers.ofString());
        })
    );
}
```

#### 처리의 핵심
- **요청/작업당 가상 스레드 하나** 패턴이 다시 실용적입니다.
- 목표는 "리액티브 체인을 모두가 작성하게 하는 것"보다, **익숙한 스레드·동기 스타일로 대량 동시성**을 얻는 것입니다.
- `synchronized`나 일부 네이티브/핀닝(pinning) 구간에서는 캐리어가 묶일 수 있어 주의가 필요합니다.

## 2. 비교 분석

### 📌 한눈에 보는 비교표

| 구분 | 고루틴 (Go) | 코루틴 (Kotlin 중심) | 가상 스레드 (Java) |
|------|-------------|----------------------|---------------------|
| **정체** | 런타임 경량 스레드 | 중단 가능한 계산 + 디스패처 | JVM 경량 스레드 |
| **스케줄러** | Go 런타임 (M:N) | 라이브러리/디스패처 | JVM (캐리어 스레드 위) |
| **코드 스타일** | `go` + 채널 | `suspend` / `async` / `await` | 기존 Thread/동기 코드 |
| **양보 방식** | I/O·채널·런타임 개입 | **명시적 suspend 지점** (협력적) | 블로킹 포인트에서 언마운트 |
| **구조화** | Context 취소가 일반적 | **Structured Concurrency 강함** | Scope/구조는 직접 설계하는 편 |
| **통신 모델** | 채널·CSP 강조 | 공유 상태 + 취소/채널성 API | 공유 메모리·락이 자연스러움 |
| **학습 곡선** | Go 동시성 모델 적응 | suspend·스코프·디스패처 이해 | 기존 Java 스레드 지식 재사용 |
| **대표 강점** | 단순함 + 대량 동시성 | 취소/계층/가독성 | 레거시 동기 코드 확장 |

### 💡 "같다 / 다르다"를 한 문장으로

- **같다**: 셋 다 **OS 스레드 남용을 피하고**, I/O 대기 동안 일손을 놀리지 않으려 합니다.
- **다르다**:  
  - Go는 **언어+런타임이 동시성을 기본값**으로 밀어 주고,  
  - Kotlin 코루틴은 **컴파일러/라이브러리가 중단점을 설계**하게 하며,  
  - Java 가상 스레드는 **플랫폼 스레드 API의 경량 구현**으로 생태계를 끌어올립니다.

### 💻 같은 문제를 세 방식으로 보면

**문제**: URL 3개를 동시에 호출해 결과를 모은다.

**Go**
```go
results := make(chan string, 3)
for _, u := range urls {
    u := u
    go func() { results <- fetch(u) }()
}
for i := 0; i < 3; i++ {
    fmt.Println(<-results)
}
```

**Kotlin**
```kotlin
coroutineScope {
    val jobs = urls.map { async { fetch(it) } }
    jobs.awaitAll().forEach(::println)
}
```

**Java (Virtual Thread)**
```java
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = urls.stream()
        .map(u -> exec.submit(() -> fetch(u)))
        .toList();
    for (var f : futures) System.out.println(f.get());
}
```

세 코드 모두 "동시에 기다린다"는 목적은 같고, **동시성을 드러내는 문법의 위치**만 다릅니다.

## 3. 제약과 맞춤 활용 가치

### 🟢 고루틴 — 제약

- 공유 메모리+락을 남용하면 **레이스**가 나기 쉽습니다. (채널/소유권 설계가 중요)
- 스택은 동적으로 커지지만, 고루틴 누수(종료되지 않는 `go`)는 여전히 위험합니다.
- CPU 밀집 작업만 잔뜩이면, 결국 **코어 수 이상의 마법**은 없습니다.

### 🟢 고루틴 — 잘 맞는 곳

- 네트워크 서버, 프록시, 워커 풀, 파이프라인 처리
- **"동시성을 언어 기본 문법으로"** 팀 전체가 쓰고 싶을 때
- 마이크로서비스·CLI·인프라성 도구처럼 **배포 단위가 단순한** 경우

---

### 🟣 코루틴 — 제약

- `suspend`를 모르는 블로킹 함수를 코루틴 스레드에서 호출하면 **스레드 풀이 고갈**될 수 있습니다.
- Dispatcher 선택(`Main` / `IO` / `Default`)을 잘못하면 성능·ANR 문제가 납니다.
- Structured Concurrency를 무시하고 GlobalScope를 남발하면 **취소·누수**가 생깁니다.
- "코루틴 = 만능 멀티스레드"가 아닙니다. **병렬 CPU 작업**과 **동시 I/O**를 구분해야 합니다.

### 🟣 코루틴 — 잘 맞는 곳

- Android / Ktor / Spring(Kotlin)처럼 **취소와 UI/요청 생명주기**가 중요한 앱
- 여러 비동기 작업을 **계층적으로 묶고 한 번에 취소**해야 할 때
- 읽기 좋은 동기 스타일 + 세밀한 동시성 제어가 필요할 때

---

### 🟠 가상 스레드 — 제약

- **핀닝(pinning)**: 오래 잡는 `synchronized`, 일부 네이티브 호출은 캐리어를 붙잡아 확장성을 깎습니다.
- 스레드 로컬을 과하게 쓰는 레거시 패턴은 가상 스레드 대량 생성과 궁합이 나쁠 수 있습니다.
- 풀 크기를 "적당히 제한"하던 튜닝 감각을, **"작업당 스레드"** 감각으로 재조정해야 합니다.
- CPU 바운드 병렬화의 해답은 여전히 **병렬 스트림/ForkJoin/고정 풀** 쪽과 역할을 나눠야 합니다.

### 🟠 가상 스레드 — 잘 맞는 곳

- **블로킹 I/O가 많은** 기존 Java/Spring 서버를 큰 리라이트 없이 확장하고 싶을 때
- 리액티브(WebFlux 등)로 가기엔 팀 숙련도·디버깅 비용이 부담될 때
- JDBC, 동기 HTTP 클라이언트, 파일 I/O처럼 **"동기 코드가 이미 자산"**인 코드베이스

---

### 📌 선택 가이드 (실무용 짧은 기준)

```
I/O 많고 Go 스택이다?                    → 고루틴이 자연스러움
취소/생명주기/모바일·Kotlin 중심?         → 코루틴
Java 동기 코드가 자산이고 대량 동시성 필요? → 가상 스레드
CPU 한계까지 쥐어짜는 연산?               → 세 모델 모두 "만능" 아님 (병렬 설계 별도)
```

## 4. 기타 알아두면 좋은 포인트

### 💡 1) "동시성(Concurrency)" ≠ "병렬성(Parallelism)"

- **동시성**: 여러 일을 **진행 가능 상태로 섞어** 다루는 구조
- **병렬성**: 여러 일을 **같은 시각에 실제로** 실행

고루틴/코루틴/가상 스레드는 우선 **동시성 도구**입니다.  
코어를 꽉 채우는 병렬 CPU 작업은 별도 설계(작업 분할, 한계 두기)가 필요합니다.

### 💡 2) 블로킹을 어디에 두느냐가 성패를 가른다

| 모델 | 위험한 실수 | 완화 |
|------|-------------|------|
| 고루틴 | 공유 상태 레이스, 종료 안 되는 고루틴 | 채널·`context` 취소 |
| 코루틴 | 블로킹 호출을 Default/Main에서 수행 | `withContext(Dispatchers.IO)` 등 |
| 가상 스레드 | 핀닝·무제한 폭주 | 동기화 최소화, 세마포어로 제한 |

### 💡 3) 디버깅·관측성도 설계 일부다

- Go: goroutine dump, `pprof`
- Kotlin: coroutine debugger, Job 계층 로그
- Java: 가상 스레드 이름/트레이싱, 핀닝 로그(`jdk.tracePinnedThreads` 등)

가볍다고 무한히 만들면, 장애 때 **"수만 개의 실행 단위"**를 관찰해야 합니다.  
생성 비용이 싸진 만큼 **수명·취소·백프레셔** 설계가 더 중요해집니다.

### 💡 4) 리액티브와의 관계

- 코루틴/가상 스레드는 **"콜백·연산자 체인 없이"** 비슷한 확장성을 노리는 쪽에 가깝습니다.
- 이미 Reactor/WebFlux가 팀 표준이라면 억지로 옮길 필요는 없고, **신규/동기 코드 영역**부터 가상 스레드를 검토하는 편이 현실니다.
- Go는 애초에 리액티브 프레임워크 없이도 고루틴이 그 역할을 상당 부분 대체합니다.

### 💡 5) 메모리·스택 감각

- 고루틴: 초기 스택이 매우 작고 필요 시 성장
- 코루틴: 스레드 스택을 작업마다 붙이지 않고, continuation 상태로 대기
- 가상 스레드: 플랫폼 스레드 대비 훨씬 가볍게 많이 올릴 수 있음

즉, **"동시 대기자 수"** 를 키우는 데는 모두 유리하고, **"동시 CPU 노동자 수"** 는 하드웨어 한계를 따릅니다.

## 마무리

세 기술을 억지로 순위를 매기기보다, 이렇게 기억하는 편이 실무에 도움이 됩니다.

- **고루틴**: 언어가 동시성을 **기본 무기**로 준 모델
- **코루틴**: 중단 가능한 코드로 **생명주기와 가독성**을 설계하는 모델
- **가상 스레드**: Java의 **동기 스레드 프로그래밍을 대규모로 부활**시킨 모델

식당으로 다시 비유하면,

> 고루틴은 **알바를 무한 고용하는 시스템**,  
> 코루틴은 **대기 구간마다 손을 바꾸는 레시피 엔진**,  
> 가상 스레드는 **창구 직원은 그대로인데 손님을 가상으로 무한히 받는 번호표 시스템**입니다.

팀의 언어·레거시·취소 요구사항·I/O 패턴에 맞춰 고르면, "무거운 스레드 지옥" 없이도 충분한 동시성을 손에 넣을 수 있습니다.

다음엔 같은 주제로 **벤치마크 관점(처리량·지연·핀닝·컨텍스트 스위칭)** 이나 **Spring Boot + Virtual Thread / Ktor + Coroutine / Go net/http** 실전 세팅도 이어서 정리해 보겠습니다. 🙌
