## 안녕하십니까! 😀

1편에서는 시스템 설계를 **요구 사항 → 상위 아키텍처 → 상세 → UI·API·DB** 순서로 진행하는 법을 정리했습니다. 그 과정에서 요구 사항을 "비기능"으로 나눴을 때, 이름만 적고 넘어간 항목이 많았습니다.

"일관성 있게", "빠르게", "안 잃어버리게", "죽지 않게"는 모두 설계를 바꾸는 **속성(Quality Attribute)** 입니다. 그런데 이 속성들은 대부분 서로 부딪힙니다. 일관성을 올리면 지연 시간이 늘고, 가용성을 올리면 일관성이 흔들리는 식입니다.

오늘은 분산 시스템을 설계할 때 자주 등장하는 여덟 가지 속성을 정의하고, 측정하는 법과 서로 충돌하는 지점을 정리합니다.

- 일관성(Consistency)
- 가용성(Availability)
- 파티션 허용성(Partition Tolerance)
- 지연 시간(Latency)
- 내구성(Durability)
- 신뢰성(Reliability)
- 장애 허용성(Fault Tolerance)
- 확장성(Scalability)

이번에도 1편과 같은 **스터디룸 예약 시스템**을 예로 들어, 각 속성이 설계에서 무엇을 바꾸는지 봅니다.

## 0. 먼저 큰 그림: 분산 시스템은 원래 실패한다

한 대의 서버에서 돌아가는 프로그램은 대부분 **전부 살거나 전부 죽습니다**. 반면 여러 대의 서버가 네트워크로 연결되면, 일부만 죽거나, 느리거나, 응답은 왔는데 **그 응답이 도착하지 않은 것처럼** 보이는 상황이 생깁니다.

```
클라이언트 ──요청──▶ 서버 A ──(처리 완료)──▶ 응답 유실
    │                                          │
    └─ 타임아웃 → 재시도 ──▶ 서버 A(또는 B)      │
                                  "이미 처리했나?" ← 여기가 어려운 지점
```

이 때문에 분산 시스템에서는 "요청이 성공했는가"를 **항상 확실히 알 수 없다**는 전제로 설계합니다. 여덟 가지 속성은 모두 이 불확실성을 어떤 규칙으로 다룰지에 대한 이야기입니다.

## 1. 일관성 (Consistency)

일관성은 **여러 복제본이나 여러 노드가 같은 데이터를 보여 줄 때, 그 값이 얼마나 일치하는가**에 대한 보장입니다. 같은 단어가 여러 의미로 쓰여서 먼저 구분합니다.

| 용어 | 뜻 | 대략 |
|------|----|------|
| **선형화 가능성(Linearizability)** | 쓰기가 끝난 뒤의 모든 읽기는 그 값을 본다. 전체가 한 줄로 줄 서 있는 것처럼 보인다 | 가장 강함 |
| **순차 일관성(Sequential)** | 모든 노드가 같은 순서로 연산을 본다. 실시간 순서는 보장하지 않을 수 있다 | 강함 |
| **인과 일관성(Causal)** | 인과 관계가 있는 연산은 모든 노드에서 같은 순서로 보인다 | 중간 |
| **읽기 자신의 쓰기(Read-your-writes)** | 내가 쓴 값은 내가 다시 읽을 때 반드시 보인다 | 사용자 체감용 |
| **최종 일관성(Eventual)** | 새 쓰기가 멈추면, 결국 모든 복제본이 같은 값으로 수렴한다 | 가장 약함 |

💡 "일관성"이라고만 말하면 팀마다 다른 뜻으로 들립니다. 설계 문서에는 **어떤 일관성인지, 어느 범위(한 키, 한 파티션, 전역)인지**를 적습니다.

### 📌 스터디룸 예시

같은 방의 같은 시간대 예약은 **이중 예약이 절대 없어야** 합니다. 이 규칙은 쓰기 직후 다른 사용자가 바로 확인할 수 있어야 하므로, 해당 키에 대해서는 강한 일관성이 필요합니다. 반대로 "방별 빈 슬롯 목록"을 검색 화면에 보여 주는 데는 **몇 초 늦은 값**이 허용될 수 있습니다.

```
예약 확정 쓰기 ──▶ PostgreSQL 주 노드 (강한 일관성, 권위 있는 값)
                         │ 비동기 복제
                         ▼
검색 화면 ◀── Redis 슬롯 캐시 (최종 일관성, 몇 초 지연 허용)
```

✏️ <span style="color: red;">일관성은 "전부 강하게"가 아니라, 데이터마다 필요한 강도를 나눠 정하는 것입니다.</span>

## 2. 가용성 (Availability)

가용성은 **시스템이 요청을 받아 응답할 수 있는 시간의 비율**입니다. 흔히 "9의 개수"로 말합니다.

| 가용성 | 한 달(30일) 중단 허용 | 1년 중단 허용 |
|--------|----------------------|---------------|
| 99% | 약 7시간 12분 | 약 3일 15시간 |
| 99.9% | 약 43분 12초 | 약 8시간 46분 |
| 99.99% | 약 4분 19초 | 약 52분 36초 |
| 99.999% | 약 26초 | 약 5분 16초 |

### 📌 직렬과 병렬이 가용성을 바꾼다

여러 컴포넌트가 **직렬로** 모두 살아 있어야 요청이 성공하면, 가용성은 곱해져 떨어집니다.

```
API (99.9%) → DB (99.9%) → 캐시 (99.9%)
전체 ≈ 0.999 × 0.999 × 0.999 ≈ 99.7%
```

반대로 **독립적인 복제본 두 개 중 하나만 살아 있으면 되는** 구조라면 가용성이 올라갑니다. 장애가 서로 독립이라는 가정이 필요하다는 점을 잊지 않습니다.

```
1 - (1 - 0.999)² ≈ 0.999999  (독립·동시 장애 없음 가정)
```

실제로는 같은 랙, 같은 배포 스크립트, 같은 인증서처럼 **상관 장애**가 있어서 이 계산보다 낮게 나옵니다.

### 📌 스터디룸 예시

예약 **검색**은 캐시나 읽기 복제본이 있으면 DB 주 노드가 잠깐 죽어도 응답할 수 있습니다. 가용성을 우선하는 기능입니다.

예약 **확정**은 일관성이 우선이므로, 주 노드가 없으면 "지금은 예약 불가"라고 명확히 실패하는 편이 낫습니다. 잘못 받아 두고 나중에 충돌을 정리하는 것보다 낫습니다.

✏️ <span style="color: red;">가용성 목표는 기능마다 다릅니다. "시스템 전체 99.9%"보다 "검색 99.95%, 예약 확정 99.9%"처럼 쪼개야 설계가 구체적이 됩니다.</span>

## 3. 파티션 허용성 (Partition Tolerance)

파티션(Partition)은 네트워크가 나뉘어 **노드들이 서로 메시지를 주고받지 못하는 상태**입니다. 서버는 살아 있는데 통신만 끊긴 상황입니다.

```
[서울 노드 A] ──X──  네트워크 단절  ──X── [부산 노드 B]
   (A는 살아 있고, B도 살아 있지만 서로 연결되지 않음)
```

### 📌 CAP 정리에서의 의미

Eric Brewer가 2000년에 제시하고 Gilbert와 Lynch가 2002년에 증명한 CAP 정리는 다음을 말합니다.

- **C**onsistency (일관성)
- **A**vailability (가용성)
- **P**artition tolerance (파티션 허용성)

네트워크 파티션이 일어난 순간에는 **C와 A 중 하나를 골라야** 합니다. 이때 **P는 선택지가 아닙니다.** 분산 시스템에서 네트워크는 언젠가 끊기므로, P를 포기하면 시스템 자체를 단일 노드로 만들어야 합니다.

| 파티션 중 선택 | 동작 | 예 |
|----------------|------|----|
| **CP** | 일관성을 지키려고 일부 요청을 거절·대기 | 단일 리더 DB에서 소수 쪽 쓰기 거절 |
| **AP** | 응답은 하되, 나중에 충돌을 정리 | 장바구니에 서로 다른 노드가 각자 항목 추가 |

💡 "CAP에서 CA를 고른다"는 말은 파티션이 없을 때만 의미가 있습니다. 실제 운영에서는 파티션이 **언제 올지 모르는 것**이 문제입니다.

### 📌 PACELC: 파티션이 없을 때는?

Daniel Abadi가 제안한 PACELC는 CAP을 확장합니다.

> 파티션(P)이 있으면 가용성(A)과 일관성(C) 중 택하고, 그렇지 않으면(E) 지연 시간(L)과 일관성(C) 중 택한다.

정상 상태에서도 동기 복제를 기다리면 지연이 늘고, 비동기 복제를 쓰면 빠르지만 읽기가 낡을 수 있습니다. 평소의 선택이 장애 때의 선택보다 더 자주 체감됩니다.

### 📌 스터디룸 예시

지점 간 설정 동기화가 끊겼을 때, 두 지점이 같은 방을 **각자 예약 가능하다고 판단**하면 이중 예약이 생깁니다. 이 시스템은 **예약 쓰기만큼은 CP**로 가는 편이 맞습니다. 대신 지점 설정 조회는 잠깐 낡아도 되므로 AP가 됩니다.

## 4. 지연 시간 (Latency)

지연 시간은 요청을 보낸 뒤 응답을 받을 때까지 걸리는 시간입니다. **평균 하나로 보면 안 됩니다.** 분산 시스템에서는 꼬리(tail)가 사용자 경험과 장애를 결정합니다.

| 지표 | 의미 |
|------|------|
| **p50** | 중앙값. 절반의 요청이 이보다 빠르다 |
| **p95** | 95%의 요청이 이 안에 끝난다 |
| **p99** | 99%의 요청이 이 안에 끝난다. 나머지 1%가 "가끔 느리다"의 정체 |
| **max** | 가장 느린 한 건. 타임아웃과 연결 |

### 📌 꼬리 지연이 증폭되는 이유

한 사용자 요청이 내부 서비스 100개를 **순서대로 또는 병렬로 모두 기다려야** 한다고 해 봅시다. 각 서비스의 응답이 1%만 느리다면, 전체 요청이 느린 것을 만날 확률은 다음과 같습니다.

```
1 - (0.99)^100 ≈ 0.63   (약 63%)
```

서비스 하나의 p99가 전체 요청의 체감 지연을 지배하게 됩니다. 그래서 **팬아웃이 큰 구조일수록 개별 서비스의 꼬리를 관리**해야 합니다.

### 📌 지연을 줄이는 대표 수단

- 캐시: 읽기 경로에서 DB 왕복을 줄임
- 비동기 처리: 사용자가 기다리지 않는 작업(알림, 집계)을 분리
- 타임아웃 설정: 무한 대기 대신 빠른 실패
- 요청 병합·배치: 작은 호출을 묶음
- 가까운 리전·엣지: 물리적 거리 단축

⚠️ 지연을 줄이려고 **동기 복제를 끄면**, 장애 시 데이터 손실 위험이 올라갑니다. 지연과 내구성은 자주 충돌합니다.

### 📌 스터디룸 예시

검색 API의 목표를 "p95 200ms 이하"로 잡았다면, 그 숫자를 구성 요소로 나눠 봅니다.

| 구간 | 예산(예시) |
|------|-----------|
| 게이트웨이·인증 | 20ms |
| 검색 서비스 로직 | 30ms |
| Redis 조회 | 5ms |
| 캐시 미스 시 DB | 80ms |
| 여유분 | 65ms |

이렇게 쪼개 두면 "어디가 느린지" 대신 "어느 예산이 초과됐는지"로 토론할 수 있습니다.

## 5. 내구성 (Durability)

내구성은 **확정된 데이터가 장애 후에도 사라지지 않는 성질**입니다. 가용성이 "지금 응답하는가"라면, 내구성은 "응답한 것을 잃지 않는가"입니다.

### 📌 쓰기 응답 시점이 곧 내구성의 기준

```
[클라이언트] ──쓰기──▶ [서버]
                        │ 1) 메모리 버퍼에만 쓰고 응답   → 장애 시 유실 가능
                        │ 2) 디스크에 fsync 후 응답      → 단일 노드 내구성
                        │ 3) 다른 노드 과반에 복제 후 응답 → 노드 장애 허용
```

응답을 빨리 보낼수록 유실 위험이 커집니다. 반대로 과반 복제를 기다리면 지연이 늘어납니다. 내구성 목표를 숫자로 적어 두면 선택이 쉬워집니다.

- RPO(Recovery Point Objective): 장애 때 **얼마 전까지의 데이터 손실을 허용하는가**
- RTO(Recovery Time Objective): 장애 후 **얼마 안에 복구해야 하는가**

### 📌 복제는 백업이 아니다

복제본이 있다고 해서 백업이 된 것은 아닙니다. 실수로 `DELETE`를 실행하면 복제본에도 그대로 전파됩니다. 그래서 다음을 함께 둡니다.

- **스냅샷/PITR(시점 복구)**: 과거 시점으로 되돌리는 능력
- **오프사이트 백업**: 같은 리전·계정이 날아가도 남는 사본
- **복구 훈련**: 백업이 실제로 복원되는지 주기적으로 확인

AWS S3는 설계 목표로 객체 내구성 99.999999999%(11 nines)를 제시합니다. 이 수치는 "데이터를 맡길 저장소의 설계 목표"이지, 우리 서비스의 백업 정책을 대신하지는 않습니다.

### 📌 스터디룸 예시

확정된 예약은 **잃으면 안 되는 데이터**입니다. 쓰기는 주 DB에서 커밋한 뒤에만 응답하고, 주 노드 장애 시에는 동기 복제본으로 승격합니다. 알림 큐의 메시지는 조금 늦게 가도 되지만, "예약은 됐는데 기록이 없음"은 허용하지 않습니다.

## 6. 신뢰성 (Reliability)

신뢰성은 **시스템이 정해진 기간 동안 기대한 대로 옳게 동작하는 확률**입니다. 가용성과 헷갈리기 쉽지만 다릅니다.

- 가용성: 응답이 **왔는가**
- 신뢰성: 응답이 **맞았는가**, 그리고 **오래 맞았는가**

응답은 200 OK로 빠르게 왔는데 잘못된 가격을 계산하면, 가용성은 100%여도 신뢰성은 낮습니다.

### 📌 신뢰성을 측정하는 방법

| 개념 | 설명 |
|------|------|
| **SLI** | 측정 지표. 예: 예약 확정 성공률 |
| **SLO** | 목표. 예: 월간 성공률 99.9% |
| **에러 버짓** | 목표를 넘어도 되는 실패 여유. 100% - 99.9% = 0.1% |

에러 버짓이 빨리 줄어들면 새 기능 배포를 늦추고 안정화에 집중하는 식으로, 신뢰성과 속도를 **숫자로 협상**할 수 있습니다.

### 📌 신뢰성을 해치는 흔한 원인

- 중복 처리: 같은 메시지를 두 번 소비해 알림이 두 번 감
- 부분 실패: 예약은 저장됐는데 캐시 갱신이 실패해 화면과 불일치
- 잘못된 재시도: 실패한 쓰기를 다른 키로 재시도해 이중 생성
- 설정 오류: 운영 시간 타임존이 UTC와 KST에서 달라짐

### 💡 체크리스트

- 같은 요청을 두 번 보내도 결과가 한 번과 같은가 (멱등성)
- 부분 실패 후 **보정 작업(재처리, 보상 트랜잭션)** 이 정의되어 있는가
- 중요한 흐름에 **자동 검증 테스트**가 있는가

---

## 7. 장애 허용성 (Fault Tolerance)

장애 허용성은 **일부 구성 요소가 실패해도 시스템 전체가 계속 목적을 달성하는 능력**입니다. 가용성이 결과라면, 장애 허용성은 그 결과를 만드는 **설계 기법**입니다.

### 📌 대표 기법

| 기법 | 하는 일 | 주의 |
|------|---------|------|
| **중복(Redundancy)** | 같은 역할의 인스턴스를 여럿 둔다 | 같은 장애 도메인에 몰리면 효과가 줄어든다 |
| **복제(Replication)** | 데이터 사본을 여러 노드에 둔다 | 일관성·지연과 트레이드오프 |
| **장애 조치(Failover)** | 주 노드가 죽으면 대기 노드를 승격한다 | 승격 중 쓰기 중단 시간, 스플릿 브레인 |
| **헬스 체크·리더 선출** | 살아 있는 노드를 감지하고 리더를 정한다 | 타임아웃이 짧으면 오탐으로 흔들림 |
| **재시도 + 백오프 + 지터** | 일시 실패를 흡수한다 | 무분별한 재시도는 장애를 증폭 |
| **서킷 브레이커** | 실패가 많은 의존성 호출을 잠시 끊는다 | 임계값·복구 조건 설계 필요 |
| **격벽(Bulkhead)** | 자원 풀을 분리해 한 곳의 폭주가 전체를 막지 않게 한다 | 풀 크기 산정 |
| **멱등성** | 같은 요청을 반복해도 한 번만 반영된다 | 키 저장과 만료 정책 필요 |

### 📌 쿼럼으로 읽고 쓰기

복제본 N개에 쓰기 W개가 확인되고 읽기 R개를 본다고 할 때, 흔히 `W + R > N`이면 읽기 집합과 최근 쓰기 집합이 **최소 한 노드에서 겹쳐** 최신 값을 볼 가능성이 생깁니다.

```
N = 3 (복제본 3개)
W = 2, R = 2  →  W + R = 4 > 3  → 읽기와 쓰기가 최소 한 노드에서 겹침

          쓰기 (W=2)
  [A ✓] [B ✓] [C  ]
          읽기 (R=2)
  [A  ] [B  ] [C  ]   ← 최소 B를 공유
```

단, 이것은 **쿼럼 설계의 기본 직관**입니다. 실패 시 임시 노드에 쓰는 "느슨한 쿼럼(sloppy quorum)"이나 클럭 문제가 섞이면 보장이 약해지므로, 실제 제품 문서의 조건을 확인해야 합니다.

### 📌 스플릿 브레인과 펜싱

네트워크가 나뉘어 두 노드가 "나도 리더"라고 믿으면 **스플릿 브레인**이 일어납니다. 대응은 다음과 같습니다.

- 다수결(과반) 없이는 리더가 쓰기를 수락하지 않는다
- 리더마다 증가하는 **펜싱 토큰**을 발급하고, 저장소가 낡은 토큰을 거절한다

### 📌 스터디룸 예시

- 예약 DB: 주 노드 + 동기 대기 노드, 장애 시 자동 승격 (CP 성격)
- 검색 서비스: 상태 없는(stateless) 인스턴스 여러 개, 한 대가 죽으면 로드밸런서가 제외
- 알림 워커: 같은 메시지를 두 번 받아도 `notification_id` 기준으로 중복 발송 방지 (멱등)
- 외부 메일 API: 실패가 연속되면 서킷 브레이커로 열고, 큐에 쌓아 두었다가 나중에 재시도

## 8. 확장성 (Scalability)

확장성은 **부하가 늘었을 때 자원을 더해 처리량을 얼마나 잘 늘릴 수 있는가**입니다. 빠르게 만드는 것(성능)과 많이 받는 것(확장성)은 다른 문제입니다.

### 📌 수직 확장과 수평 확장

| 방식 | 장점 | 한계 |
|------|------|------|
| **수직(Scale up)** | 구조 변경이 적다 | 장비 한계, 단일 장애점 유지 |
| **수평(Scale out)** | 한계를 늘릴 수 있다 | 데이터 분산, 조인·트랜잭션이 어려워짐 |

애플리케이션 서버는 **상태를 밖으로 빼면** 수평 확장이 쉽습니다. 병목은 대개 **상태를 가진 저장소**로 옮겨 갑니다.

### 📌 샤딩과 핫 키

데이터를 키 기준으로 나누는 것이 샤딩입니다. 키 선택이 나쁘면 한 샤드에 요청이 몰립니다.

```
샤드 키: 방 ID(room_id)
  r-101 → Shard 1
  r-102 → Shard 2
  r-103 → Shard 3

  인기 방 하나에 예약이 몰리면 Shard 1만 뜨거워짐 (핫 키)
```

핫 키 대응:

- 키에 접미사를 붙여 나눔(예: `room_id + 날짜 버킷`)
- 읽기는 복제본, 쓰기는 큐로 흡수
- 가상 노드 기반 재배치로 편중 완화

### 📌 확장과 다른 속성의 충돌

- 샤딩을 하면 **여러 샤드에 걸친 트랜잭션**이 어려워져 일관성 보장 비용이 커집니다.
- 노드가 늘면 **조정 비용**(합의, 락, 헬스 체크)이 늘어 지연이 올라갈 수 있습니다.
- 확장 중 리밸런싱은 **일시적 지연과 부분 실패**를 만듭니다.

따라서 확장성 목표도 "몇 배까지"만 말하지 말고 **무엇이 먼저 병목이 되는지**까지 적습니다.

### 📌 스터디룸 예시

지점이 10곳에서 100곳으로 늘어도, 예약 데이터는 `branch_id`로 나누면 지점 간 쓰기가 서로 간섭하지 않습니다. 다만 "전국 인기 방 검색" 같은 교차 지점 쿼리는 샤드를 가로지르므로, 검색 전용 읽기 모델(인덱스 복제본)을 따로 두는 편이 낫습니다.

---

## 9. 속성 사이의 충돌: 설계는 트레이드오프다

여덟 속성은 서로 **동시에 최대치로 가질 수 없습니다.** 대표적인 충돌은 다음과 같습니다.

| 강화하면 | 약해지기 쉬운 것 | 이유 |
|----------|------------------|------|
| 강한 일관성 | 가용성, 지연 | 합의·동기 복제를 기다림 |
| 비동기 복제 | 내구성, 일관성 | 응답 후 장애 시 최신 쓰기 유실 가능 |
| 많은 재시도 | 지연, 신뢰성 | 중복 처리·부하 증폭 |
| 샤딩 확대 | 일관성 조정 비용 | 교차 샤드 트랜잭션 증가 |
| 촘촘한 헬스 체크 | 안정성 | 짧은 타임아웃으로 오탐 증가 |

✏️ <span style="color: red;">좋은 설계 문서는 "모두 보장한다"가 아니라, **이 기능에서는 무엇을 양보했는지**를 적습니다.</span>

### 📌 스터디룸 속성 표 (요약)

| 속성 | 스터디룸에서의 목표 | 설계 선택 |
|------|--------------------|-----------|
| 일관성 | 같은 슬롯 이중 예약 금지 | 방+시작 시각 유니크, 강한 쓰기 |
| 가용성 | 검색 99.95% | 읽기 복제본과 캐시 |
| 파티션 허용성 | 지점 간 단절 가능 | 예약 쓰기는 CP, 설정 조회는 AP |
| 지연 시간 | 검색 p95 200ms | 예산 분해, 캐시, 비동기 알림 |
| 내구성 | 확정 예약 유실 0 | 동기 복제, PITR 백업 |
| 신뢰성 | 잘못된 확정·취소 0 | 멱등 키, 상태 전이 규칙 테스트 |
| 장애 허용성 | DB 주 노드 장애에도 예약 복구 | 자동 failover, 재시도 정책 |
| 확장성 | 지점 100곳 | `branch_id` 샤딩, 검색 모델 분리 |

## 10. 설계 문서에 넣는 방법

속성을 말로만 나열하면 구현으로 이어지지 않습니다. 다음 순서로 문서에 고정하면 좋습니다.

1. **목표를 숫자로**: 가용성 99.9%, 검색 p95 200ms, RPO 0초 같은 값
2. **데이터별 등급**: 예약은 강한 일관성, 알림은 최종 일관성 등
3. **실패 시나리오**: 노드 다운, 네트워크 단절, 중복 메시지, 디스크 가득 참
4. **각 시나리오의 기대 동작**: 거절할지, 대기할지, 낡은 값을 줄지
5. **검증 방법**: 장애 주입 테스트, 부하 테스트, 복구 훈련

이 다섯 가지가 있으면, 1편의 상위 아키텍처 박스와 DB 제약이 "왜 그렇게 생겼는지"를 설명할 수 있습니다.

## 마무리

분산 시스템 설계는 여덟 개의 단어를 외우는 일이 아니라, **네트워크가 끊기고 서버가 죽는 세계에서 무엇을 약속할지 정하는 일**입니다.

- **일관성**: 누가 언제 무엇을 보느냐
- **가용성**: 응답할 수 있느냐
- **파티션 허용성**: 네트워크가 끊겨도 시스템이 남아 있느냐
- **지연 시간**: 꼬리까지 포함해 얼마나 빠르냐
- **내구성**: 응답한 것을 잃지 않느냐
- **신뢰성**: 맞는 응답을 오래 주느냐
- **장애 허용성**: 일부가 죽어도 목적을 달성하느냐
- **확장성**: 부하가 늘어도 처리량을 더할 수 있느냐

다음 편에서는 이 속성들을 실제로 조정하는 도구인 **캐시, 큐, 로드 밸런싱, 샤딩 전략**을 같은 스터디룸 예시로 정리하겠습니다. 🙌

감사합니다!
