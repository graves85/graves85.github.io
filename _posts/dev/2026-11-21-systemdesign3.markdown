## 0. 이론을 왜 알아야 하는가

분산 시스템에서는 세 가지가 동시에 성립하지 않는 경우가 많습니다.

1. 모든 노드가 **항상** 같은 값을 본다
2. 모든 요청에 **항상** 응답한다
3. 네트워크가 **절대** 끊기지 않는다

이론의 역할은 "모두 보장한다"를 막는 것입니다. 대신 **어느 가정을 두고, 무엇을 양보할지**를 명확히 합니다. 구현 패턴(캐시, 샤딩, 합의)은 그 선택 위에 올라갑니다.

```
[가정과 불가능성]
  CAP / PACELC / FLP / 비잔티움
           │
           ▼
[합의와 리더]
  Paxos / Raft
           │
           ▼
[데이터 배치와 근사 구조]
  Consistent Hashing / Bloom / CMS / HLL
```

## 1. CAP 정리

### 📌 한 줄로

> 네트워크 파티션이 일어난 순간, 시스템은 **강한 일관성(C)** 과 **가용성(A)** 중 하나만 지킬 수 있다. **파티션 허용성(P)** 은 분산 시스템에서 사실상 전제다.

Eric Brewer가 2000년 PODC에서 제안하고, Seth Gilbert와 Nancy Lynch가 2002년에 형식화했습니다. 여기서의 일관성은 대략 **선형화 가능성(Linearizability)** 에 가깝습니다. "쓰기 완료 후 모든 읽기가 그 값을 본다"는 의미입니다.

### 📌 파티션이 생겼을 때의 선택

```
        파티션 발생
             │
    ┌────────┴────────┐
    ▼                 ▼
   CP                 AP
일관성 유지          응답 유지
(일부 요청 거절)    (값이 어긋날 수 있음)
```

| 선택 | 동작 | 예 |
|------|------|----|
| **CP** | 소수 쪽은 쓰기·최신 읽기를 거절하거나 대기 | ZooKeeper, etcd, 단일 리더 RDB의 소수 파티션 |
| **AP** | 양쪽에 응답하되, 나중에 충돌을 합침 | Dynamo 계열, Cassandra의 느슨한 설정 |

💡 "우리는 CA를 고른다"는 말은 **파티션이 없을 때**의 이야기입니다. 실제 운영에서는 파티션이 **언젠가 온다**고 보는 편이 안전합니다. 그래서 분산 시스템 설계의 CAP 논의는 대개 **CP vs AP**입니다.

### 📌 스터디룸 예시

같은 `(room_id, start_at)` 슬롯의 **이중 예약을 금지**하려면, 파티션 중에도 "양쪽이 각자 예약을 받아 두는" AP를 택하면 안 됩니다. 예약 쓰기는 **CP**에 가깝게 두고, 검색용 캐시는 잠깐 낡아도 되는 **AP 성격의 읽기**로 둡니다.

✏️ <span style="color: red;">CAP은 시스템 전체를 한 글자로 낙인찍는 도구가 아니라, **데이터·연산마다** C와 A 중 무엇을 양보할지 고르는 틀입니다.</span>

## 2. PACELC 정리

### 📌 한 줄로

> 파티션(P)이 있으면 Availability와 Consistency 중 택하고, Else(평상시)에는 Latency와 Consistency 중 택한다.

Daniel Abadi가 CAP만으로는 **평소의 트레이드오프**가 잘 안 보인다고 지적하며 제안했습니다. 장애가 없어도 동기 복제를 기다리면 지연이 늘고, 비동기 복제를 쓰면 빠르지만 읽기가 낡을 수 있습니다.

### 📌 표로 보면

| 상황 | 선택지 | 의미 |
|------|--------|------|
| **P** (파티션) | **A** 또는 **C** | 응답할 것인가, 일관성을 지킬 것인가 |
| **EL** (평상시) | **L** 또는 **C** | 빠르게 응답할 것인가, 강한 일관성을 기다릴 것인가 |

제품 문서에서 자주 쓰는 표기입니다.

| 표기 | 파티션 시 | 평상시 | 감각 |
|------|-----------|--------|------|
| **PA/EL** | 가용성 | 지연 우선 | Dynamo 계열에 가깝다 |
| **PC/EC** | 일관성 | 일관성 | 합의 기반 메타데이터 저장소 |
| **PA/EC** | 가용성 | 일관성 | 평소엔 강하게, 단절 시엔 응답 |
| **PC/EL** | 일관성 | 지연 우선 | 단절 시엔 거절, 평소엔 빠르게 |

### 📌 스터디룸 예시

- 예약 확정: **PC/EC** — 파티션이면 거절, 평소에도 주 DB 커밋을 기다림
- 빈 슬롯 검색 캐시: **PA/EL** — 단절·장애 시에도 오래된 목록을 줄 수 있고, 평소에도 캐시로 지연을 줄임

2편에서 말한 "검색은 가용성, 확정은 일관성"이 PACELC로 다시 적힌 것입니다.

## 3. 팩소스(Paxos)와 래프트(Raft)

합의(Consensus)는 **여러 노드가 하나의 값에 합의**하는 문제입니다. 리더 선출, 복제 로그의 다음 엔트리, 설정 변경처럼 "한 줄로 줄 세워야 하는" 작업에 쓰입니다.

### 📌 팩소스 — 안전성은 증명됐지만 구현이 어렵다

Leslie Lamport의 Paxos는 **비비잔티움(크래시·메시지 유실)** 환경에서 안전성(Safety)을 보장하는 고전입니다. 기본 흐름은 대략 두 단계입니다.

1. **Prepare / Promise**: 제안 번호 `n`으로 과반에게 "이 번호로 제안해도 되나"를 물음
2. **Accept / Accepted**: 과반이 약속하면 값 `v`를 수락 요청. 과반이 수락하면 결정(Chosen)

```
Proposer                Acceptors(과반)
   │  Prepare(n)  ──────▶│
   │◀──── Promise(n, …) │
   │  Accept(n, v) ─────▶│
   │◀──── Accepted      │
   │  → v 가 Chosen
```

Paxos는 이론적으로 탄탄하지만, Multi-Paxos·리더·로그 복제·멤버십 변경까지 붙이면 구현과 설명이 복잡해집니다. 그래서 실무 교육·많은 신형 저장소는 Raft를 선호합니다.

### 📌 래프트 — "이해하기 쉬운" 합의

Diego Ongaro와 John Ousterhout의 Raft는 **복제 상태 머신**을 목표로, 역할을 세 가지로 나눕니다.

| 역할 | 하는 일 |
|------|---------|
| **Leader** | 클라이언트 요청을 받아 로그에 쓰고, 팔로워에 복제 |
| **Follower** | 리더의 AppendEntries를 받아 로그를 맞춤 |
| **Candidate** | 리더가 없으면 선거에 나감 |

핵심 규칙입니다.

- 같은 임기(term)에 리더는 **최대 하나**
- 로그 엔트리는 인덱스와 term으로 식별
- 커밋은 **현재 임기의 엔트리가 과반에 복제**된 뒤
- 새 리더는 자신의 로그보다 앞선 미확정 엔트리를 덮어쓸 수 있음 (불완전 복제 정리)

```
Follower ──타임아웃──▶ Candidate ──과반 투표──▶ Leader
   ▲                      │ 낙선/새 임기
   └──── AppendEntries ───┘
```

etcd, Consul, TiKV 등 많은 시스템이 Raft(또는 Raft 변형)를 씁니다. ZooKeeper의 Zab도 "로그를 합의로 복제한다"는 같은 가족입니다.

### 📌 스터디룸 예시

방 메타데이터나 "어느 DB가 주 노드인가" 같은 **클러스터 설정**은 Raft/etcd에 두고, 예약 트랜잭션 자체는 PostgreSQL에 둡니다. 합의 알고리즘을 모든 예약 쓰기에 직접 얹으면 지연 비용이 커집니다. **합의가 필요한 범위**를 좁히는 것이 설계입니다.

⚠️ Paxos/Raft는 보통 **정직한 노드가 크래시하거나 느려지는** 모델을 가정합니다. 거짓 메시지를 보내는 악성 노드는 다음 절의 비잔티움 모델입니다.

## 4. 비잔티움 장군 문제

### 📌 한 줄로

> 배신자가 섞인 장군들이 **같은 작전(공격/후퇴)** 에 합의할 수 있는가?

Leslie Lamport, Robert Shostak, Marshall Pease의 고전입니다. 메시지가 위조되거나 노드가 악의적으로 다른 값을 보내도, 정직한 노드들이 같은 결정에 도달할 수 있는지가 핵심입니다.

### 📌 직관적인 한계

동기 네트워크에서 구두 메시지(Oral messages) 모델일 때, 고전적인 결과는 대략 다음과 같습니다.

> 배신자가 `f`명이면, 전체 장군이 **`3f + 1`명 이상**이어야 합의가 가능하다.

`f = 1`이면 최소 4명이 필요합니다. 3명만 있으면 배신자 한 명이 양쪽에게 다른 말을 해 정직한 둘을 갈라놓을 수 있습니다.

```
정직한 A     배신자 B     정직한 C
   │  "공격" ←── B ──→ "후퇴"  │
   └──────── 서로 다른 정보를 믿음 ────────┘
```

### 📌 PBFT와 블록체인

- **PBFT**(Practical Byzantine Fault Tolerance): 실용적인 BFT 합의. 지연과 메시지 비용이 크지만, 허가형(permissioned) 환경에서 쓰입니다.
- **블록체인·PoW/PoS**: 공개·비허가 환경에서 다른 가정(경제적 비용, 지분)으로 비잔티움 행동을 억제합니다. 모델이 Paxos/Raft와는 다릅니다.

### 📌 스터디룸 예시

사내 예약 API 클러스터는 보통 **크래시 장애**만 가정합니다. 노드가 해킹되어 거짓 예약을 주입하는 시나리오는 **인증·인가·감사 로그·서명**으로 다루는 편이 일반적입니다. BFT는 비용이 커서, 금융 정산·허가형 원장처럼 **적대적 참가자를 전제하는 도메인**에 더 자주 등장합니다.

✏️ <span style="color: red;">"장애 허용"과 "비잔티움 장애 허용"은 다릅니다. 전자는 죽음·지연, 후자는 거짓말까지 포함합니다.</span>

## 5. FLP 불가능성 정리

### 📌 한 줄로

> **완전 비동기** 메시지 전달 모델에서, 단 **하나**의 프로세스라도 멈출 수 있다면, **결정적(deterministic)** 합의 알고리즘은 모든 실행에서 종료를 보장할 수 없다.

Fischer, Lynch, Paterson의 1985년 결과입니다. 이름이 세 저자의 이니셜입니다.

### 📌 무엇이 "불가능"인가

가정입니다.

- 메시지는 결국 도착할 수 있지만, **지연에 상한이 없다** (완전 비동기)
- 최대 한 프로세스가 크래시할 수 있다
- 알고리즘은 결정적이다 (같은 상태에서 같은 다음 동작)

결론입니다.

> 안전성(잘못된 합의 금지)과 활동성(언젠가는 합의)을 **동시에, 모든 실행에서** 보장하는 결정적 프로토콜은 없다.

### 📌 그런데 왜 Raft는 돌아가는가

실무 시스템은 FLP를 "어기는" 것이 아니라, **가정을 바꿉니다.**

| 실무 장치 | FLP 가정을 어떻게 완화하는가 |
|-----------|------------------------------|
| **타임아웃·하트비트** | 완전 비동기를 포기하고, "이만큼 기다리면 죽었다 본다" |
| **무작위화** | 결정성을 깨 교착 가능성을 확률적으로 줄임 |
| **부분 동기** | 언젠가부터는 메시지 지연에 상한이 있다고 가정 |
| **실패 감지기** | 의심→제거로 활동성을 회복 (오탐 시 안전성은 별도 규칙으로 지킴) |

💡 FLP는 "합의를 만들지 말라"가 아니라, **비동기만으로는 종료를 절대 보장할 수 없다**는 경고입니다. 타임아웃을 넣는 순간, 그 타임아웃이 틀릴 때의 동작(스플릿 브레인 방지)을 설계해야 합니다.

### 📌 스터디룸 예시

리더 선출에 "3초 동안 하트비트가 없으면 후보가 된다"는 규칙이 있다면, 그것은 FLP가 말하는 완전 비동기를 포기한 것입니다. 네트워크가 일시적으로 느려 **살아 있는 리더를 죽은 줄 알면** 선거가 일어납니다. 이때 Raft의 term·투표 규칙이 두 리더가 동시에 커밋하지 못하게 막습니다.

## 6. 일관된 해싱 (Consistent Hashing)

### 📌 한 줄로

> 노드가 늘거나 줄어도, 키의 **대부분**이 같은 노드에 남도록 배치하는 해시 기법이다.

일반 `hash(key) % N`은 노드 수 `N`이 바뀔 때마다 **거의 모든 키**가 재배치됩니다. 일관된 해싱은 해시 공간을 링으로 보고, 노드와 키를 같은 원에 배치합니다.

```
        0
    k1      N2
  N1          k3
    k2      N3
        …
```

키는 시계 방향으로 **자신 이상인 첫 노드**에 할당됩니다. 노드가 하나 빠져도, 그 노드가 담당하던 구간만 이웃으로 이동합니다.

### 📌 가상 노드(VNode)

노드마다 해시 링에 점 하나만 찍으면, 구간 길이가 들쭉날쭉해 부하가 편중됩니다. 그래서 물리 노드마다 **가상 노드를 여러 개** 올려 균형을 맞춥니다.

| 개념 | 역할 |
|------|------|
| **해시 링** | 0 ~ 2^m − 1 같은 원형 공간 |
| **가상 노드** | 물리 노드의 부하를 고르게 분산 |
| **복제** | 시계 방향 다음 N−1개 노드에 사본 (Dynamo 스타일) |

Amazon Dynamo 논문, Cassandra, 일부 CDN·캐시 프록시가 이 아이디어를 사용합니다. Ketama 같은 라이브러리 이름도 자주 등장합니다.

### 📌 스터디룸 예시

지점이 100곳으로 늘 때 예약 캐시를 서버 여러 대에 나눈다면:

- `hash(branch_id) % 서버수` → 서버 추가 시 캐시가 대량 미스
- 일관된 해싱 → 추가된 서버 구간의 키만 이동

핫 키(인기 방)는 해싱만으로 해결되지 않습니다. 2편에서 말한 것처럼 **키를 더 쪼개거나**, 그 키만 별도 계층으로 빼는 설계가 필요합니다.

## 7. 블룸 필터 (Bloom Filter)

### 📌 한 줄로

> 집합에 **원소가 확실히 없는지는 말할 수 있고**, **있다고 하면 틀릴 수 있는**(거짓 양성) 공간 효율적인 확률적 자료구조다.

비트 배열과 여러 해시 함수로 구성합니다.

1. 삽입: 원소를 `k`개 해시로 보내 해당 비트를 1로 둠
2. 질의: `k`개 비트가 모두 1이면 "있을 수 있음", 하나라도 0이면 **"없음"이 확실**

```
비트 배열:  [0 1 0 1 1 0 1 0 …]
해시1(x) → 1, 해시2(x) → 3, 해시3(x) → 4  → 모두 1이면 후보
```

### 📌 성질

| 항목 | 내용 |
|------|------|
| **거짓 음성** | 없음 (정상 구현 기준). "없다"면 정말 없음 |
| **거짓 양성** | 있음. 차있으면 올라감 |
| **삭제** | 기본형에서는 어려움. Counting Bloom 등이 필요 |
| **크기** | 원소 수·허용 오차에 따라 비트 수와 `k`를 설계 |

### 📌 어디에 쓰나

- DB·캐시 앞에서 **"없는 키"를 빠르게 걸러** 비싼 조회를 줄임 (예: 일부 LSM 엔진의 SSTable 필터)
- 크롤러·추천에서 "이미 본 URL인가"
- CDN·보안에서 대량 멤버십 근사

### 📌 스터디룸 예시

취소·만료된 예약 ID에 대한 조회가 많다면, "최근에 존재했던 reservation_id" 블룸 필터를 API 앞에 둘 수 있습니다. 필터가 "없음"이면 DB를 안 치고 404를 주고, "있음"일 때만 DB를 봅니다. 거짓 양성이면 가끔 불필요한 DB 조회가 나가지만, **없는 ID 스캔 공격**의 부하를 크게 줄입니다.

## 8. 카운트-민 스케치 (Count-Min Sketch)

### 📌 한 줄로

> 스트림에서 **각 원소의 빈도**를 작게 추정하는 스케치다. 추정값은 **실제보다 작지 않은** 쪽(과대 추정)으로 치우친다.

`d`개의 해시 행과 `w`개의 열을 가진 테이블을 둡니다. 원소가 올 때마다 각 행에서 해시된 칸을 1 증가시키고, 질의 시에는 **각 행 값의 최솟값**을 추정치로 씁니다.

```
행1: hash1(x) → +1
행2: hash2(x) → +1
행3: hash3(x) → +1

추정(x) = min(행1[h1(x)], 행2[h2(x)], 행3[h3(x)])
```

충돌 때문에 다른 원소의 카운트가 섞여 **과대**될 수 있지만, 최솟값을 취해 과대를 줄입니다. 메모리는 `O(d·w)`로 원소 종류 수와 무관하게 고정할 수 있습니다.

### 📌 블룸 필터와 비교

| | 블룸 필터 | Count-Min Sketch |
|--|-----------|------------------|
| 질문 | 집합에 있는가 | 몇 번 나타났는가 |
| 오차 | 거짓 양성 | 빈도 과대 추정 |
| 전형 용도 | 멤버십 | 핫 키·상위 N·이상 탐지 |

### 📌 스터디룸 예시

피크 시간대에 **어떤 방·슬롯 검색이 폭주하는지**를 전수 카운터로 모으면 카드내틸리티가 큽니다. API 게이트웨이에서 Count-Min Sketch로 `room_id` 빈도를 근사하면, 핫 키 캐시 승격·레이트 리밋·알람을 적은 메모리로 걸 수 있습니다. 정확한 정산·이중 예약 방지에는 쓰지 말고, **관측과 완화**에 쓰는 것이 맞습니다.

## 9. 하이퍼로그로그 (HyperLogLog)

### 📌 한 줄로

> 거대한 스트림에서 **서로 다른 값의 개수(cardinality)** 를 작은 메모리로 추정한다.

아이디어의 뼈대입니다.

1. 값을 해시하면 비트열이 나온다
2. 앞쪽 0이 길게 이어질수록, 그런 패턴은 **드물다** → 집합이 컸을 가능성이 높다
3. 해시 공간을 여러 **버킷(레지스터)** 으로 나누고, 각 버킷에 "본 최대 선행 0 길이"를 저장
4. 버킷들을 조화 평균 비슷한 방식으로 합쳐 전체 카디널리티를 추정

원형 HyperLogLog는 수 KB ~ 수십 KB로 **수억·수십억** 규모의 distinct를 근사할 수 있습니다. Redis의 `PFADD` / `PFCOUNT`가 이 계열입니다.

### 📌 오차와 병합

- 표준 오차는 레지스터 수에 따라 대략 `1.04 / √m` 수준으로 줄어듭니다
- 같은 설정의 HLL끼리 **병합**이 쉬워, 샤드·리전별로 센 뒤 합칠 수 있습니다

| 자료구조 | 잘하는 질문 |
|----------|-------------|
| Bloom | 이 값이 집합에 있는가 |
| Count-Min | 이 값이 몇 번인가 |
| HyperLogLog | 서로 다른 값이 몇 개인가 |

### 📌 스터디룸 예시

"오늘 검색을 시도한 **고유 회원 수**", "이번 주 예약을 조회한 **고유 IP**"처럼 정확한 집합을 다 저장하기 부담스러울 때 HLL이 맞습니다. 청구·좌석 수처럼 **한 자리도 틀리면 안 되는 숫자**에는 쓰면 안 되고, 대시보드·용량 계획·이상 탐지에 씁니다.

## 10. 이론을 설계에 꽂는 법

이름을 외우는 것보다, 문서에 **한 줄 결정**으로 남기는 편이 낫습니다.

| 이론 | 설계 문서에 남길 문장 예 |
|------|--------------------------|
| CAP | "예약 쓰기는 파티션 시 거절(CP), 검색 캐시는 낡은 값 허용(AP)" |
| PACELC | "확정은 PC/EC, 검색은 PA/EL" |
| Paxos/Raft | "클러스터 멤버십·리더는 etcd(Raft), 예약 데이터는 PostgreSQL" |
| 비잔티움 | "내부 노드는 크래시 모델, 외부 클라이언트는 인증으로 적대 행위 차단" |
| FLP | "리더 감지는 3s 타임아웃, 오탐 시 term으로 이중 리더 커밋 방지" |
| 일관된 해싱 | "캐시 노드 증설 시 키 이동 최소화, vnode 200개/노드" |
| Bloom | "없는 reservation_id는 필터로 차단 후 404" |
| Count-Min | "room_id 핫 키 근사로 캐시 승격" |
| HyperLogLog | "일별 고유 검색 사용자 대시보드" |

✏️ <span style="color: red;">정확한 돈이 오가는 경로에는 근사 구조(Bloom/CMS/HLL)를 쓰지 않습니다. 합의·강한 일관성이 필요한 좁은 핵과, 관측·가속을 위한 바깥을 나눕니다.</span>

## 마무리

3편에서 본 이론은 세 층으로 기억하면 됩니다.

1. **무엇을 동시에 약속할 수 없는가** — CAP, PACELC, FLP, 비잔티움  
2. **여러 노드가 한 값에 합의하려면** — Paxos, Raft (그리고 가정의 차이)  
3. **대규모 데이터를 싸게 다루려면** — 일관된 해싱, 블룸 필터, Count-Min Sketch, HyperLogLog  

2편의 속성(일관성·가용성·지연·확장성)이 "목표"라면, 오늘의 이론은 **그 목표가 왜 충돌하고, 어떤 도구로 타협하는지**를 설명합니다.
