## 1. 컨테이너 가상화 기술이란? (VM vs Docker)

기존의 가상 머신(VM) 방식과 컨테이너 기반 가상화의 구조적 차이를 이해하는 것이 도커의 출발점입니다.

```
[ 가상 머신 (VM) ]                     [ 도커 컨테이너 (Docker) ]
┌─────────────────────────┐           ┌─────────────────────────┐
│ App A  │ App B  │ App C │           │ App A  │ App B  │ App C │
├────────┼────────┼───────┤           ├────────┼────────┼───────┤
│ Bins/  │ Bins/  │ Bins/ │           │ Bins/  │ Bins/  │ Bins/ │
│ Libs   │ Libs   │ Libs  │           │ Libs   │ Libs   │ Libs  │
├────────┼────────┼───────┤           ├─────────────────────────┤
│ Guest  │ Guest  │ Guest │           │     Docker Engine       │
│  OS    │  OS    │  OS   │           │ (Container Runtime)     │
├─────────────────────────┤           ├─────────────────────────┤
│  Hypervisor (Type 1/2)  │           │   Host OS Kernel (Linux)│
├─────────────────────────┤           ├─────────────────────────┤
│     Host OS / Server    │           │     Host Hardware       │
└─────────────────────────┘           └─────────────────────────┘
```

### 📊 VM vs Docker 컨테이너 비교

| 비교 항목 | 가상 머신 (VM / Hypervisor) | 도커 컨테이너 (Docker Container) |
| :--- | :--- | :--- |
| **격리 수준** | **하드웨어 수준의 완전 가상화** | **OS 커널 수준의 프로세스 격리** (Namespace, cgroups) |
| **Guest OS 유무** | **각 VM마다 독립된 Guest OS 필요** (수 GB 크기) | **Guest OS 없음 (Host OS 커널 공유)** |
| **부팅 속도** | 분(Minute) 단위 (OS 전체 부팅 필요) | **초(Second) / 밀리초 단위** (단순 프로세스 시작) |
| **리소스 오버헤드** | OS 구동으로 인한 무거운 CPU/메모리 오버헤드 | **거의 무시할 수 있는 수준의 가벼운 오버헤드** |
| **이식성** | VM 이미지 용량이 수~수십 GB로 이동 무거움 | **수십~수백 MB 단위 이미지로 초고속 배포 가능** |

> 💡 **핵심 원리**: 도커는 리눅스 커널의 **`cgroups`(자원 제한)**와 **`namespaces`(프로세스, 네트워크, 파일시스템 격리)** 기술을 활용하여 호스트 커널을 공유하면서도 독립된 공간에서 실행되는 격리된 프로세스입니다.

## 2. 도커 이미지(Image)와 컨테이너(Container)

- **도커 이미지(Image)**: 애플리케이션 실행에 필요한 코드, 런타임, 라이브러리, 환경 설정 등을 하나로 패키징한 **불변의 읽기 전용 템플릿(Read-Only Blueprint)**입니다.
- **도커 컨테이너(Container)**: 이미지를 기반으로 생성되어 독립된 공간에서 실행되는 **인스턴스(실행 주체)**입니다. 하나의 이미지로 여러 컨테이너를 복제하여 실행할 수 있습니다.

### 📌 레이어 기반 파일시스템 (Union File System)
도커 이미지는 여러 개의 읽기 전용 레이어(Read-Only Layers)가 계층형으로 쌓인 구조입니다. 컨테이너를 실행하면 그 위에 **쓰기 가능한 얇은 레이어(Container Read-Write Layer)** 1개만 올려서 변경 사항을 기록합니다.

```
┌──────────────────────────────────────┐
│  Container Write Layer (R/W)         │ ◄ 컨테이너 실행 중 생성/수정된 파일
├──────────────────────────────────────┤
│  Layer 3: CMD ["java", "-jar", ...]  │ (Read-Only Image Layer)
├──────────────────────────────────────┤
│  Layer 2: COPY app.jar /app/         │ (Read-Only Image Layer)
├──────────────────────────────────────┤
│  Layer 1: Base Image (OpenJDK)       │ (Read-Only Image Layer)
└──────────────────────────────────────┘
```

### 🔄 컨테이너 생명주기 (Lifecycle)
1. **Created**: 이미지를 기반으로 컨테이너가 생성된 상태 (`docker create`)
2. **Running**: 컨테이너가 실행되어 프로세스가 동작 중인 상태 (`docker start`, `docker run`)
3. **Paused**: 프로세스가 일시 정지된 상태 (`docker pause`)
4. **Stopped (Exited)**: 프로세스가 정상 종료되었거나 중지된 상태 (`docker stop`)
5. **Deleted**: 컨테이너가 파일시스템에서 완전히 제거된 상태 (`docker rm`)

## 3. 효율적인 이미지 빌드와 Dockerfile 작성법

이미지를 생성하는 방법은 크게 두 가지가 있습니다.
1. 기존 컨테이너를 수정한 뒤 `docker commit`으로 굽는 방법 (비추천: 히스토리 추적 및 재현성 어려움)
2. **Dockerfile 스크립트를 작성하여 `docker build`하는 방법 (표준 방식)**

### 📌 Dockerfile 핵심 명령어

| 명령어 | 설명 및 용도 |
| :--- | :--- |
| `FROM` | 기반이 될 베이스 이미지 지정 (예: `FROM eclipse-temurin:21-jre-alpine`) |
| `WORKDIR` | 컨테이너 내부의 기본 작업 디렉토리 설정 |
| `COPY` | 호스트 머신의 파일/디렉토리를 컨테이너 내부로 복사 |
| `RUN` | 이미지 빌드 과정에서 실행할 리눅스 셸 명령어 (패키지 설치, 빌드 등) |
| `ENV` / `ARG` | 환경변수 설정 (`ENV`: 런타임 유지, `ARG`: 빌드 시에만 사용) |
| `EXPOSE` | 문서화 목적으로 컨테이너가 수신 대기할 포트 명시 |
| `ENTRYPOINT` | 컨테이너가 시작될 때 고정으로 실행할 메인 명령어 |
| `CMD` | 컨테이너 기본 실행 인자 (docker run 시 오버라이딩 가능) |

---

### 🚀 멀티 스테이지 빌드 (Multi-stage Build) 실무 예제

Java/Spring이나 Go, Node.js 애플리케이션을 빌드할 때 소스 코드 빌드 도구(Maven/Gradle, JDK 등)는 런타임에 불필요합니다.
**멀티 스테이지 빌드**를 활용하면 최종 배포 이미지의 용량을 80% 이상 획기적으로 줄일 수 있습니다.

```dockerfile
# 1단계: 빌드 환경 (Build Stage)
FROM gradle:8.5-jdk21-alpine AS builder
WORKDIR /build

# 빌드 캐시 최적화: 소스코드보다 dependencies 파일을 먼저 복사
COPY build.gradle settings.gradle /build/
RUN gradle build -x test --parallel --continue > /dev/null 2>&1 || true

# 전체 소스 복사 후 JAR 빌드
COPY src /build/src
RUN gradle bootJar -x test --no-daemon

# 2단계: 실행 환경 (Runtime Stage - 가벼운 JRE Alpine 사용)
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app

# 보안을 위해 Non-Root 사용자 생성 및 전환
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

# 1단계 빌더에서 생성된 순수 실행 파일(JAR)만 복사
COPY --from=builder /build/build/libs/*.jar /app/app.jar

# JVM 메모리 최적화 옵션 및 실행
ENV JAVA_OPTS="-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0"
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar /app/app.jar"]
```

## 4. 도커 네트워크 (Docker Network)

컨테이너는 기본적으로 호스트 머신과 격리된 네트워크 인터페이스(veth)를 가지며, 외부 통신 및 컨테이너 간 통신을 위해 네트워크 드라이버를 제공합니다.

```
[호스트 머신 (Host IP: 192.168.1.100)]
   │
   ├─ 포트포워딩 (-p 8080:80)
   ▼
[docker0 Bridge Network (172.17.0.0/16)]
   ├── [ Container A (172.17.0.2:80) ]
   └── [ Container B (172.17.0.3:8080) ]
```

### 📌 주요 네트워크 드라이버 종류
1. **Bridge (기본값)**: 동일 호스트 내 컨테이너들이 가상 브릿지(`docker0`)를 통해 통신
2. **Host**: 컨테이너가 호스트의 네트워크 네임스페이스를 직접 공유 (포트 매핑 불필요, 최고 성능)
3. **Overlay**: 여러 호스트(다중 서버/클러스터)에 걸쳐 있는 컨테이너 간 통신 지원 (Docker Swarm 등)
4. **None**: 네트워크 인터페이스를 아예 비활성화 (완전 격리)

> 💡 **실무 TIP**: 기본 `bridge` 네트워크는 컨테이너 IP로만 통신 가능하지만, **사용자 정의 브릿지(User-defined Network)**(`docker network create my-net`)를 생성하여 연결하면 **컨테이너 이름(도메인명)으로 편리하게 통신(DNS Service Discovery)**할 수 있습니다.

## 5. 도커 스토리지와 볼륨 (Volume Management)

컨테이너는 **"소모품(Cattle)"** 방식으로 관리되므로 컨테이너가 삭제되면 내부 데이터도 함께 사라집니다. 데이터베이스(MySQL, Redis 등)나 업로드 파일처럼 영구 보존이 필요한 데이터는 **볼륨(Volume)**을 마운트해야 합니다.

```
1. Volume (-v my-vol:/data): Docker가 관리하는 호스트 영역 (/var/lib/docker/volumes/)
2. Bind Mount (-v /host/path:/data): 호스트의 특정 절대 경로를 직접 마운트
3. tmpfs Mount (--tmpfs /data): 호스트의 메인 메모리(RAM)에만 임시 저장
```

| 구분 | Volume (볼륨) | Bind Mount (바인드 마운트) |
| :--- | :--- | :--- |
| **저장 위치** | Docker 전용 스토리지 디렉토리 | 호스트 OS의 모든 파일 시스템 경로 |
| **Docker 관리 여부** | Docker CLI(`docker volume`)로 직접 관리 | 사용자가 직접 파일 경로 관리 |
| **권장 사용처** | **DB 데이터, 영속성 보존 데이터 (운영 환경 권장)** | 로컬 개발 시 소스코드 실시간 핫리로드, 호스트 설정 파일 주입 |

## 6. 실무에서 꼭 알아두어야 할 필수 최적화 TIP

### 💡 1. 레이어 캐싱(Layer Caching)을 고려한 명령어 순서 배치
- Dockerfile은 위에서 아래로 실행되며, 변경된 라인 이후의 모든 레이어는 캐시가 깨집니다.
- 자주 변경되지 않는 기본 설정(`FROM`, 의존성 매니페스트 파일 복사 등)을 상단에 두고, 자주 바뀌는 소스코드(`COPY . .`)는 하단에 배치해야 빌드 속도가 극대화됩니다.

### 💡 2. `.dockerignore` 파일 필수 활용
- `.git`, `node_modules`, `build`, `.env` 같은 불필요한 파일과 민감 정보가 빌드 컨텍스트에 포함되지 않도록 `.dockerignore`를 반드시 작성합니다.

### 💡 3. 경량화 베이스 이미지 선택 (Alpine / Distroless)
- `ubuntu`나 일반 `openjdk` 대신 **`alpine`** 또는 보안 취약점을 최소화한 구글의 **`distroless`** 이미지를 사용하여 이미지 크기를 줄이고 공격 표면(Attack Surface)을 축소합니다.

### 💡 4. 컨테이너 내부 JVM 메모리 설정 (`-XX:MaxRAMPercentage`)
- Java 컨테이너가 메모리 부족으로 강제 종료(`OOMKilled, Exit Code 137`)되는 것을 방지하기 위해, `-Xmx` 절대값 대신 **컨테이너 제한 메모리의 70~75%**를 힙으로 잡도록 `-XX:+UseContainerSupport -XX:MaxRAMPercentage=75.0` 옵션을 지정합니다.

### 💡 5. Root 사용자로 실행하지 않기 (보안)
- 기본적으로 컨테이너는 `root` 사용자로 실행됩니다. 보안 취약점 방지를 위해 `USER` 명령어를 통해 제한된 권한의 일반 사용자로 프로세스를 실행해야 합니다.

## 7. 자주 사용하는 핵심 Docker 명령어 치트시트

```bash
# 1. 이미지 빌드 및 실행
docker build -t my-app:1.0 .
docker run -d -p 8080:8080 --name my-app --network my-net my-app:1.0

# 2. 컨테이너 상태 및 로그 확인
docker ps -a
docker logs -f --tail 100 my-app

# 3. 컨테이너 내부 접속 디버깅
docker exec -it my-app /bin/sh

# 4. 사용하지 않는 리소스 일괄 정리 (용량 확보)
docker system prune -a --volumes
```

## 8. 마치며 & 요약 정리

도커는 컨테이너 기술을 통해 애플리케이션의 개발부터 배포, 운영까지의 환경 불일치를 해소해 주는 가장 강력한 도구입니다.

- **컨테이너 본질**: Guest OS 없이 호스트 커널을 공유하며 프로세스를 격리(Namespace, cgroups)하는 초경량 가상화
- **이미지와 컨테이너**: 불변의 읽기 전용 레이어(Image) + 실행 중 쓰기 레이어(Container)
- **멀티 스테이지 빌드**: 빌드 단계와 런타임 단계를 분리하여 최소 용량의 초경량 배포 이미지 생성
- **네트워크와 스토리지**: 사용자 정의 브릿지로 DNS 통신, 볼륨(Volume)을 통한 데이터 영속성 보장

도커의 기초를 단단히 다져두면, 이후 쿠버네티스(Kubernetes)나 클라우드 기반 MSA 환경으로 확장할 때 훨씬 수월하게 인프라를 이해하고 다룰 수 있습니다!
