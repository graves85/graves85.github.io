## 안녕하십니까! 😀

현대 대규모 트래픽을 처리하는 백엔드 아키텍처와 마이크로서비스(MSA) 환경에서 가장 널리 쓰이는 핵심 데이터 파이프라인 기술 중 하나가 바로 **아파치 카프카(Apache Kafka)**입니다.

서비스 규모가 커짐에 따라 시스템 간의 의존성이 복잡해지고, 대량의 이벤트를 실시간으로 유실 없이 처리해야 하는 요구사항이 늘어나게 됩니다. 카프카는 이러한 문제를 해결하는 데 있어 사실상의 표준(De-facto Standard)으로 자리 잡았습니다.

오늘은 **Kafka의 기본 개념**, **웹 서비스에서 카프카를 도입하는 이유**, **실무 사용 사례**, **RabbitMQ와의 차이점 및 선택 기준**, **반드시 알아야 할 핵심 용어(acks 등)**, 그리고 **실무 필수 TIP**까지 한 번에 정리해보겠습니다! 🚀

## 1. Kafka란?

**아파치 카프카(Apache Kafka)**는 대용량 실시간 데이터 스트림을 빠르고 안정적으로 수집, 저장, 처리하기 위해 링크드인(LinkedIn)에서 최초 개발하고 오픈소스화한 **분산 이벤트 스트리밍 플랫폼(Distributed Event Streaming Platform)**입니다.

기존의 단순 메시지 큐(Message Queue) 시스템과 달리, 카프카는 **이벤트(로그)를 디스크에 영속적으로 순차 기록(Append-only Log)**하고 여러 컨슈머가 원하는 시점에 데이터를 읽어갈 수 있도록 설계되었습니다.

### 📌 Kafka의 핵심 특징

1. **초고성능 대용량 처리 (High Throughput & Low Latency)**
   - 디스크 순차 I/O(Sequential I/O), 페이지 캐시(Page Cache) 활용, 제로 카피(Zero-Copy) 기술을 통해 초당 수십만~수백만 건의 이벤트를 극도로 낮은 지연 시간으로 처리합니다.
2. **높은 확장성(Scalability) 및 고가용성(High Availability)**
   - 클러스터 구성으로 브로커(Broker) 노드를 수평 확장(Scale-out)할 수 있으며, 파티션 복제(Replication)를 통해 특정 노드가 죽어도 무중단 운영이 가능합니다.
3. **영속성(Durability)과 재생(Replayability)**
   - 메시지를 컨슈머가 소비하더라도 바로 삭제하지 않고 설정된 보관 주기(Retention) 동안 디스크에 안전하게 보관합니다. 장애 발생 시 오프셋을 되돌려 메시지를 재처리(Replay)할 수 있습니다.
4. **발행/구독(Pub/Sub) 모델**
   - 프로듀서와 컨슈머가 완벽하게 분리(Decoupling)되어 독립적으로 동작합니다.

## 2. Kafka를 웹 서비스에서 사용하는 이유

웹 서비스 아키텍처가 모놀리식에서 마이크로서비스(MSA)로 전환되고 트래픽이 증가할수록 Kafka의 필요성이 커집니다.

```
[AS-IS: 강한 결합 (Point-to-Point)]
주문 서비스 ──(동기 HTTP 호출)──► 결제 서비스
주문 서비스 ──(동기 HTTP 호출)──► 알림 서비스
주문 서비스 ──(동기 HTTP 호출)──► 배송/재고 서비스
* 한 서비스 장애 시 전체 장애 전파 & 응답 지연

[TO-BE: Kafka를 통한 느슨한 결합 (Event-Driven)]
주문 서비스 ──► [ Kafka Topic: order-created ] 
                     │
                     ├──► 결제 서비스 (비동기 처리)
                     ├──► 알림 서비스 (비동기 처리)
                     └──► 배송/재고 서비스 (비동기 처리)
```

### 1) 서비스 간 결합도 완화 (Decoupling)
- 시스템들이 직접 통신(동기 REST API)하지 않고 카프카를 통해 이벤트를 주고받으므로, 새로운 서비스가 추가되거나 기존 서비스가 일시 중단되어도 전체 시스템에 장애가 전파되지 않습니다.

### 2) 비동기 처리를 통한 사용자 응답 속도 향상
- 사용자의 주문 요청 시, 핵심 로직(주문 생성)만 처리 후 이벤트를 카프카로 발행하고 즉시 사용자에게 성공 응답을 반환합니다. (알림톡 발송, 통계 적재, 쿠폰 지급 등은 백그라운드 비동기 처리)

### 3) 트래픽 버퍼링 및 피크 부하 해소 (Load Leveling)
- 이벤트/할인 행사 등으로 갑작스러운 트래픽 폭증이 발생해도, 카프카가 큐 역할을 하여 데이터를 버퍼링해주므로 백엔드 서버나 DB가 과부하로 다운되는 것을 방지합니다.

## 3. Kafka 실무 사용 사례

### ① 마이크로서비스 간 비동기 이벤트 통신 (Event-Driven Architecture)
- 주문 완료, 회원가입, 결제 승인 등의 도메인 이벤트를 발행하여 다른 마이크로서비스들이 해당 이벤트를 구독하고 후속 작업을 처리합니다. (Saga 패턴을 통한 분산 트랜잭션 구현)

### ② 대용량 로그 수집 및 데이터 파이프라인
- 수많은 웹/앱 서버에서 발생하는 접속 로그, 클릭 스트림(Clickstream), API 요청 로그를 실시간 수집하여 Elasticsearch, Hadoop, Data Lake(S3) 등으로 전달합니다.

### ③ 실시간 데이터 스트리밍 & 모니터링
- 이상 거래 탐지(FDS, Fraud Detection), 실시간 추천 시스템, 실시간 지표 집계 등에 Kafka Streams나 Flink/Spark와 연계하여 스트림 처리를 수행합니다.

### ④ CDC(Change Data Capture) 기반 데이터 동기화
- Debezium 등의 도구를 이용해 메인 DB(MySQL 등)의 변경 데이터(binlog)를 카프카로 실시간 캡처하고, 검색 엔진(Elasticsearch)이나 캐시(Redis)에 실시간 동기화합니다.

## 4. Kafka VS RabbitMQ 중 어떤 걸 사용해야 할까?

메시징 브로커를 선택할 때 가장 많이 비교되는 대상이 바로 **RabbitMQ**입니다. 두 기술은 지향하는 철학과 최적의 유스케이스가 다릅니다.

### 📊 비교 분석표

| 비교 항목 | Apache Kafka | RabbitMQ |
| :--- | :--- | :--- |
| **시스템 유형** | **분산 이벤트 스트리밍 플랫폼 (Append-only Log)** | **전통적인 메시지 브로커 (Message Queue)** |
| **데이터 전달 방식** | **Pull 모델** (컨슈머가 원하는 속도로 가져감) | **Push 모델** (브로커가 컨슈머에게 밀어넣음) |
| **메시지 소비 후 처리** | **보관 주기에 따라 보존** (소비 후에도 유지, 재처리 가능) | **컨슈머가 소비/Ack 시 큐에서 즉시 삭제** |
| **처리량 (Throughput)** | **압도적으로 높음 (초당 수백만 건 가능)** | 높음 (초당 수만~수십만 건) |
| **라우팅 복잡도** | 단순 (Topic / Partition 기반 라우팅) | **매우 유연하고 복잡함 (Exchange, Routing Key 등)** |
| **메시지 순서 보장** | **파티션(Partition) 단위 엄격한 순서 보장** | 단일 큐 내에서는 보장되나 복수 컨슈머 시 어려움 |
| **운영 복잡도** | 상대적으로 높음 (클러스터, 파티션 튜닝 필요) | 비교적 쉬움 (직관적인 관리 Web UI 제공) |

---

### 💡 선택 가이드

#### 👉 이럴 때는 RabbitMQ를 추천합니다!
- **복잡한 라우팅 규칙(Wildcard, Topic Exchange 등)**이 필요한 경우
- 작업 큐(Work Queue), 백그라운드 배치 작업 분배 등 **전통적인 메시지 큐 요건**
- 메시지 단위로 우선순위(Priority Queue), 지연 전송(Delayed Message) 처리가 필요한 경우
- 초당 수만 건 내외의 트래픽이며 **빠른 구축과 손쉬운 관리/웹 UI가 필요한 환경**

#### 👉 이럴 때는 Kafka를 추천합니다!
- **초당 수십만~수백만 건 이상의 대규모 데이터 스트림/로그 처리**가 필요한 경우
- 메시지 소비 후에도 데이터를 보관하고 장애 시 **과거 메시지 재처리(Replay)가 필수적인 경우**
- 대규모 MSA 환경의 **중앙 이벤트 허브(Event Backbone)** 구축
- **파티션 단위의 엄격한 메시지 순서 보장**이 필요한 경우

## 5. Kafka를 사용하려면 꼭 알아두어야 할 핵심 용어들

카프카를 다루기 위해 반드시 숙지해야 하는 핵심 용어들입니다.

```
[Producer] ──(acks=all)──► [ Topic: order-events ]
                             ├── Partition 0  [0][1][2][3][4]... (Offset)
                             └── Partition 1  [0][1][2]...
                                      ▲
                                      └── [Consumer Group] (Consumer 1, 2)
```

1. **Broker (브로커)**: 카프카 서버 인스턴스를 의미하며, 데이터를 수신/저장하고 컨슈머에게 전달합니다.
2. **Topic (토픽)**: 메시지를 논리적으로 구분하는 채널(카테고리)입니다. (예: `order-events`, `user-signup`)
3. **Partition (파티션)**: 토픽을 물리적으로 나눈 단위입니다. 병렬 처리의 기본 단위이며, 각 파티션 내부에서만 메시지 순서가 엄격하게 보장됩니다.
4. **Offset (오프셋)**: 파티션 내에서 각 메시지가 가지는 고유한 순차 번호(ID)입니다. 컨슈머는 자신이 어디까지 읽었는지를 `Consumer Offset`으로 기록합니다.
5. **Producer & Consumer**: 메시지를 생성하여 발행하는 주체(Producer)와 메시지를 읽어서 처리하는 주체(Consumer)입니다.
6. **Consumer Group (컨슈머 그룹)**: 동일한 목적으로 토픽을 구독하는 컨슈머들의 논리적 묶음입니다. 한 파티션은 동일 컨슈머 그룹 내에서 **오직 하나의 컨슈머만** 할당받아 처리하므로, 컨슈머 간 경합 없이 안전하게 병렬 확장이 가능합니다.
7. **acks (Producer Acknowledgment)**: 프로듀서가 브로커에게 메시지를 보낸 후 쓰기 성공 여부를 확인하는 정책입니다.
   - `acks=0`: 브로커 응답을 기다리지 않고 즉시 다음 메시지 전송 (최고 속도, 유실 가능성 높음)
   - `acks=1`: 리더(Leader) 파티션에만 정상 기록되면 성공 응답 반환 (기본값, 팔로워 복제 전 리더 장애 시 유실 가능)
   - `acks=all` (또는 `-1`): 리더 및 최소 복제 수(`min.insync.replicas`)의 팔로워까지 모두 정상 복제된 후 응답 (최고의 신뢰성, 데이터 유실 방지 필수 설정)

## 6. Kafka를 사용할 때 꼭 알아두어야 할 필수 TIP

실무에서 카프카를 운영하면서 겪기 쉬운 문제들을 예방하기 위한 핵심 팁들입니다.

### 💡 1. 데이터 유실 없는 전송을 위한 3대 설정 조합
데이터 유실이 절대 발생하면 안 되는 비즈니스(결제, 주문 등)에서는 아래 3가지 설정을 반드시 함께 맞춰야 합니다.
- Producer: `acks=all`
- Producer: `enable.idempotence=true` (멱등성 프로듀서 활성화: 네트워크 재시도로 인한 중복 전송 방지)
- Topic / Broker: `min.insync.replicas=2` (복제본이 최소 2개 이상 동기화되어야 쓰기 성공 처리)

### 💡 2. 파티션(Partition) 개수는 신중하게 결정하기 (축소 불가!)
- 카프카에서 **파티션 개수는 늘릴 수는 있지만 줄일 수는 없습니다.**
- 처음부터 너무 많은 파티션을 생성하면 파일 핸들러 리소스 낭비와 리밸런싱 비용이 증가합니다. 예상되는 컨슈머 처리량(TPS)에 맞춰 적절한 개수로 시작한 뒤 필요에 따라 증설하는 것이 좋습니다.

### 💡 3. 컨슈머는 반드시 멱등성(Idempotent)을 갖추어 구현하기
- 분산 네트워크 환경에서 "정확히 한 번(Exactly-once)" 처리는 네트워크 타임아웃, 리밸런싱 등으로 인해 어렵습니다. 카프카의 기본 전달 보장은 **최소 한 번(At-least-once)**입니다.
- 따라서 컨슈머 측에서는 동일한 메시지가 두 번 수신되더라도 DB의 고유 키(Unique Key)나 Redis 처리 이력 체크 등을 통해 **중복 처리되지 않도록 멱등한 로직**을 반드시 구현해야 합니다.

### 💡 4. 메시지 키(Key) 사용 시 주의점
- 메시지에 Key를 지정하면 같은 Key를 가진 메시지는 항상 동일한 파티션으로 전송되어 순서가 보장됩니다.
- 하지만 특정 Key에 트래픽이 몰리면 특정 파티션에만 데이터가 편향되는 **파티션 핫스팟(Data Skew)**이 발생할 수 있으므로, 키 설계에 주의해야 합니다.

### 💡 5. `max.poll.interval.ms`와 컨슈머 타임아웃 관리
- 컨슈머가 `poll()`을 통해 메시지를 가져온 후 처리 시간이 `max.poll.interval.ms`를 초과하면, 브로커는 컨슈머가 죽은 것으로 간주하고 **컨슈머 그룹 리밸런싱(Rebalance)**을 발생시킵니다.
- 배치 처리 건수(`max.poll.records`)를 줄이거나 컨슈머 처리 로직을 가볍게 유지하여 불필요한 잦은 리밸런싱을 방지해야 합니다.

## 7. 마치며 & 요약 정리

카프카는 현대 대규모 웹 서비스와 마이크로서비스 아키텍처에서 안정적인 데이터 파이프라인과 비동기 처리를 담당하는 핵심 기술입니다.

- **Kafka란**: 대용량 실시간 데이터를 영속적으로 순차 기록하고 분산 처리하는 이벤트 스트리밍 플랫폼
- **도입 이유**: MSA 간 결합도 완화, 비동기 응답 속도 향상, 피크 트래픽 버퍼링
- **Kafka vs RabbitMQ**: 
  - 유연한 라우팅 + 복잡한 큐잉 + 즉각 삭제 $\rightarrow$ **RabbitMQ**
  - 대용량 처리 + 이벤트 재생(Replay) + 엄격한 파티션 순서 보장 $\rightarrow$ **Kafka**
- **필수 팁**: `acks=all` & `min.insync.replicas=2`로 유실 방지, 컨슈머의 멱등성 보장, 무분별한 파티션 증설 주의
