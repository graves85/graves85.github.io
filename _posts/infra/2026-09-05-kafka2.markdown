## 1. KRaft 설정 — 메타데이터 쿼럼을 제대로 잡기

1편에서 말씀드렸듯, Kafka 4.x부터는 **KRaft 전용**입니다. 외부 ZooKeeper 없이 컨트롤러 쿼럼이 `__cluster_metadata` 로그로 클러스터 메타데이터를 관리합니다.

### 📌 핵심 프로퍼티

| 프로퍼티 | 설명 | 이런 상황에 주로 사용 |
|---|---|---|
| `process.roles` | 노드 역할. `broker`, `controller`, 또는 `broker,controller`(Combined) | **운영/프로덕션**: `broker`와 `controller`를 **분리**. Combined는 로컬·개발·PoC용 |
| `node.id` | 클러스터 전역에서 유일해야 하는 노드 ID | 컨트롤러·브로커를 통틀어 **중복 없이** 부여 (예: 컨트롤러 1~3, 브로커 10~) |
| `controller.quorum.voters` | 정적 쿼럼. `id@host:port` 목록으로 투표 멤버 고정 | Kafka 3.x 계열·정적 구성. 신규 동적 쿼럼 환경에서는 점차 `bootstrap.servers` 방식으로 전환 |
| `controller.quorum.bootstrap.servers` | 컨트롤러 발견용 부트스트랩 주소 | 동적 컨트롤러 쿼럼(Dynamic Quorum) 사용 시. 클라이언트의 `bootstrap.servers`와 유사한 역할 |
| `listeners` | 이 노드가 bind하는 리스너 (프로토콜://호스트:포트) | 컨트롤러 전용 포트(`CONTROLLER://`)와 브로커 클라이언트 포트(`PLAINTEXT://`/`SSL://`) 분리 |
| `advertised.listeners` | 클라이언트가 실제로 접속할 주소 | 컨테이너/클라우드처럼 **내부 IP ≠ 외부 접속 주소**일 때 필수. 잘못 잡으면 클라이언트가 브로커를 못 찾음 |
| `listener.security.protocol.map` | 리스너 이름 → 보안 프로토콜 매핑 | `CONTROLLER:PLAINTEXT`, `EXTERNAL:SSL`처럼 역할별 프로토콜을 나눌 때 |
| `controller.listener.names` | 컨트롤러 통신에 쓸 리스너 이름 | 프로덕션에서 컨트롤러 트래픽을 데이터 플레인과 **물리/논리적으로 분리**할 때 |
| `inter.broker.listener.name` | 브로커 간 복제·하트비트용 리스너 | 클라이언트용 리스너와 분리해 **내부 복제 트래픽**을 격리할 때 |
| `log.dirs` / `metadata.log.dir` | 데이터 로그 / 메타데이터 로그 디렉터리 | 프로덕션에서는 메타데이터 로그를 **전용 빠른 SSD**에 두는 것을 권장 |

### 💡 Combined vs Isolated

```
[개발/PoC — Combined]
process.roles=broker,controller
→ 한 프로세스가 둘 다 수행. 구성은 단순하지만 컨트롤러가 트래픽 영향에 노출됨

[프로덕션 — Isolated (권장)]
Controller 노드 3대(또는 5대): process.roles=controller
Broker 노드 N대:              process.roles=broker
→ 롤링 재시작·스케일 아웃을 역할별로 분리 가능, 장애 반경(Blast Radius) 축소
```

### 💡 쿼럼 크기 가이드

- 컨트롤러는 **홀수(3 또는 5)**가 일반적입니다.
- Raft는 과반수(majority)가 살아 있어야 가용합니다.
  - 컨트롤러 3대 → 동시 장애 **1대**까지 허용
  - 컨트롤러 5대 → 동시 장애 **2대**까지 허용
- 비용·복잡도 대비 대부분 서비스는 **컨트롤러 3대 + 브로커 3대 이상**으로 시작합니다.

### 📝 KRaft 컨트롤러 예시 (`server.properties` 일부)

```properties
process.roles=controller
node.id=1
controller.quorum.voters=1@controller-1:9093,2@controller-2:9093,3@controller-3:9093

listeners=CONTROLLER://:9093
controller.listener.names=CONTROLLER
listener.security.protocol.map=CONTROLLER:PLAINTEXT

log.dirs=/var/kafka/controller-logs
# 가능하면 metadata.log.dir 을 더 빠른 디스크에 분리
```

## 2. 브로커 설정 — 데이터 플레인의 뼈대

브로커는 실제 메시지 저장·복제·클라이언트 I/O를 담당합니다. "기본값 그대로" 두면 개발에는 충분하지만, **유실 방지·디스크·네트워크** 관점에서 꼭 손볼 값이 있습니다.

### 📌 핵심 프로퍼티

| 프로퍼티 | 설명 | 이런 상황에 주로 사용 |
|---|---|---|
| `broker.id` / `node.id` | 브로커 식별자 (KRaft에서는 `node.id`) | 클러스터 전역 유일 ID. 교체·재투입 시에도 정책적으로 관리 |
| `num.network.threads` | 네트워크 I/O 스레드 수 | 클라이언트 연결·요청이 많은 고트래픽 브로커 |
| `num.io.threads` | 디스크 I/O 스레드 수 | 디스크 대역폭이 충분하고 쓰기 부하가 큰 환경 |
| `socket.send.buffer.bytes` / `socket.receive.buffer.bytes` | 소켓 송수신 버퍼 | 고지연·대용량 네트워크 구간 튜닝 시 |
| `log.dirs` | 파티션 로그가 쌓이는 디렉터리(복수 가능) | 디스크를 여러 개 붙여 **I/O 분산**할 때. 단일 거대 볼륨보다 다중 디스크가 유리한 경우가 많음 |
| `num.partitions` | 토픽 생성 시 기본 파티션 수 | 팀 표준이 있을 때. 다만 **토픽별 명시 생성**을 더 권장 |
| `default.replication.factor` | 기본 복제본 수 | 프로덕션 권장 **3**. 브로커 1대 장애에도 쓰기/읽기 유지 |
| `min.insync.replicas` | ISR(동기화된 복제본) 최소 개수 | **유실 방지 필수**. `acks=all`과 함께 `2`로 설정하는 조합이 실무 표준 |
| `unclean.leader.election.enable` | ISR 밖 복제본을 리더로 승격 허용 여부 | 기본 `false` 유지 권장. `true`는 가용성↑ but **데이터 유실 가능** — 로그/메트릭처럼 유실 감수 가능한 토픽만 예외 검토 |
| `auto.create.topics.enable` | 없는 토픽 자동 생성 | 프로덕션에서는 **`false` 권장**. 의도치 않은 토픽·잘못된 파티션 수 방지 |
| `delete.topic.enable` | 토픽 삭제 허용 | 운영 편의 vs 실수 삭제 위험. 권한(ACL)·변경관리와 함께 결정 |
| `log.retention.hours` / `log.retention.bytes` | 시간/용량 기준 보관 기간 | 규정·재처리 필요에 맞춰 설정. 결제 이벤트는 길게, 클릭 로그는 짧게 |
| `log.segment.bytes` | 세그먼트 파일 크기 | 기본(1GB)로 시작하는 경우가 많음. 너무 작으면 파일 수↑, 너무 크면 삭제·컴팩션 단위가 커짐 |
| `log.cleanup.policy` | `delete` / `compact` / 둘 다 | 일반 이벤트=`delete`, 최신 상태만 유지(예: 유저 프로필 스냅샷)=`compact` |
| `message.max.bytes` | 브로커가 수신 허용하는 최대 메시지 크기 | 대용량 페이로드(이미지 메타+본문 등)가 필요할 때. **프로듀서·토픽·브로커를 함께** 맞춰야 함 |
| `replica.fetch.max.bytes` | 팔로워가 한 번에 가져오는 최대 바이트 | 큰 메시지·고처리량 복제 환경 |
| `num.replica.fetchers` | 복제용 fetcher 스레드 수 | 팔로워 랙(lag)이 상시 높을 때 증설 검토 |
| `offsets.topic.replication.factor` | `__consumer_offsets` 복제본 수 | 프로덕션에서 **3** 권장. 오프셋 토픽 장애 = 컨슈머 커밋 장애 |
| `transaction.state.log.replication.factor` | 트랜잭션 상태 로그 복제본 수 | Exactly-once / 트랜잭션 프로듀서 사용 시 **3** 권장 |
| `group.initial.rebalance.delay.ms` | 신규 그룹 첫 리밸런스 지연 | 배포 시 컨슈머가 한꺼번에 붙을 때 **불필요한 연속 리밸런스**를 줄임 |

### 💡 유실 방지의 브로커 쪽 핵심 조합

```
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
auto.create.topics.enable=false
```

프로듀서 `acks=all` + `enable.idempotence=true`와 맞물려야 "쓰기 성공 = 최소 복제본까지 반영"이 됩니다. (1편 TIP 복습!)

## 3. 토픽 설정 — 생성 명령과 예외·재처리 토픽 설계

토픽은 **파티션 수·복제본·보관 정책**이 곧 처리량과 장애 내성의 설계서입니다. 파티션은 **늘릴 수는 있어도 줄일 수 없다**는 점만 기억하셔도 실수가 크게 줄어듭니다.

### 📌 토픽 생성 시 자주 쓰는 옵션

| 옵션 / 설정 | 설명 | 이런 상황에 주로 사용 |
|---|---|---|
| `--partitions` | 파티션 수 = 동일 컨슈머 그룹 내 최대 병렬도 | 예상 컨슈머 수·목표 TPS에 맞춰 산정. 키 순서 보장이 필요하면 키 설계와 함께 결정 |
| `--replication-factor` | 복제본 수 | 프로덕션 **3** |
| `min.insync.replicas` | 토픽 단위 ISR 하한 | 브로커 기본값과 다르게 **중요 토픽만 더 엄격**하게 줄 때 |
| `retention.ms` / `retention.bytes` | 보관 기간/용량 | 재처리·감사(Audit) 요구사항에 맞춤 |
| `cleanup.policy` | delete / compact | 이벤트 스트림 vs 상태 스토어성 토픽 |
| `max.message.bytes` | 토픽별 최대 메시지 크기 | 브로커 전역 한도를 올리지 않고 **특정 토픽만** 허용할 때 |
| `compression.type` | 토픽 측 압축 (`producer`/`gzip`/`lz4`/`zstd` 등) | 스토리지·네트워크 절감. 실무에선 `lz4`/`zstd`를 자주 검토 |
| `segment.ms` | 세그먼트 롤링 주기 | 시간 기반 삭제·컴팩션을 더 촘촘히 가져가고 싶을 때 |

### 📝 기본 토픽 생성 예시

```bash
# 주문 이벤트 (유실 민감)
kafka-topics.sh --bootstrap-server broker-1:9092 \
  --create --topic order.created \
  --partitions 12 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=604800000 \
  --config compression.type=lz4

# 클릭 로그 (상대적으로 유실 허용 가능, 짧은 보관)
kafka-topics.sh --bootstrap-server broker-1:9092 \
  --create --topic user.click \
  --partitions 24 \
  --replication-factor 3 \
  --config retention.ms=172800000
```

### 📌 예외·재처리 토픽 구성 (Retry / DLT)

실무에서는 "실패하면 그냥 커밋"하거나 "무한 재시도로 파티션을 막아버리는" 두 극단을 피해야 합니다.  
권장 패턴은 **메인 → 재시도(Retry) → 최종 실패(DLT/DLQ)** 입니다.

```
[정상]
Producer ──► order.created ──► Consumer (성공) ──► offset commit

[일시 실패 — 재시도]
Consumer 실패 ──► order.created.retry ──(지연 후)──► 재소비
  · 네트워크 순간 장애, 의존 API 5xx, DB 락 타임아웃 등

[영구 실패 — DLT]
N회 재시도 후에도 실패 ──► order.created.dlt
  · 스키마 불일치, 비즈니스 검증 실패, 복구 불가 데이터
  · 알림 + 수동/배치 재처리, 원본 오프셋·예외 메시지 헤더에 보존
```

### 📝 예외·재처리 토픽 생성 예시

```bash
# 1) 메인 토픽
kafka-topics.sh --bootstrap-server broker-1:9092 \
  --create --topic order.created \
  --partitions 12 --replication-factor 3 \
  --config min.insync.replicas=2

# 2) 재시도 토픽 (메인과 동일 파티션 수를 맞추면 키 순서 유지에 유리)
kafka-topics.sh --bootstrap-server broker-1:9092 \
  --create --topic order.created.retry \
  --partitions 12 --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=172800000

# 3) Dead Letter Topic (분석·수동 재처리용, 보관 기간을 더 길게)
kafka-topics.sh --bootstrap-server broker-1:9092 \
  --create --topic order.created.dlt \
  --partitions 6 --replication-factor 3 \
  --config min.insync.replicas=2 \
  --config retention.ms=2592000000
```

### 💡 Spring Kafka 기준 재처리 구성 감각 (개념 예시)

```java
// 개념 예시: FixedBackOff로 즉시 재시도 → 소진 시 DLT로 전송
DeadLetterPublishingRecoverer recoverer =
    new DeadLetterPublishingRecoverer(kafkaTemplate);

DefaultErrorHandler errorHandler =
    new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3L));

// 컨테이너 팩토리에 errorHandler 등록
factory.setCommonErrorHandler(errorHandler);
```

실무 팁:

1. **일시 오류**와 **영구 오류**를 코드에서 구분하세요. (재시도 의미 없는 4xx/검증 실패는 바로 DLT)
2. DLT 메시지에는 `원본 토픽`, `파티션`, `오프셋`, `예외 클래스`, `시도 횟수`를 헤더로 남기세요.
3. Retry 토픽을 여러 단계(`retry-5s`, `retry-1m`, `retry-10m`)로 나누는 **지연 재시도(Delayed Retry)** 패턴도 트래픽이 큰 서비스에서 자주 씁니다.

## 4. 프로듀서 설정 — "얼마나 빠르게, 얼마나 안전하게" 쓸 것인가

프로듀서 설정은 **처리량(Throughput)** 과 **내구성(Durability)** 의 저울입니다.

### 📌 핵심 프로퍼티

| 프로퍼티 | 설명 | 이런 상황에 주로 사용 |
|---|---|---|
| `bootstrap.servers` | 초기 접속 브로커 목록 | 최소 2~3개 이상 적어 **단일 브로커 장애 시에도** 메타데이터를 받게 |
| `key.serializer` / `value.serializer` | 직렬화기 | JSON/Avro/Protobuf 등 팀 표준에 맞춤. 스키마 레지스트리 연동 시 Avro/Protobuf 선호 |
| `acks` | 쓰기 성공 조건 (`0`/`1`/`all`) | 결제·주문 등 유실 불가 → **`all`**. 메트릭·로그성 → `1` 검토 가능 |
| `enable.idempotence` | 멱등 프로듀서 (PID+시퀀스로 중복 방지) | 재시도가 있는 모든 프로덕션 프로듀서에 **`true` 권장** (Kafka 3.x+ 기본 true인 경우 많음) |
| `retries` / `delivery.timeout.ms` | 재시도 횟수 / 전송 완료 시한 | 일시 네트워크 장애 흡수. `delivery.timeout.ms` 안에서 재시도하도록 설계 |
| `max.in.flight.requests.per.connection` | 응답 대기 중 보낼 수 있는 요청 수 | 멱등성 사용 시 **5 이하** 유지(최신 클라이언트는 멱등+순서 보장 조건 충족). 순서 초엄격이면 1도 검토 |
| `linger.ms` | 배치를 위해 잠시 대기 | 처리량 중시(수 ms~수십 ms). 초저지연 API면 `0`에 가깝게 |
| `batch.size` | 배치 최대 바이트 | `linger.ms`와 함께 튜닝. 작으면 요청 수↑, 크면 메모리·지연↑ |
| `buffer.memory` | 프로듀서 전체 버퍼 | 발행 폭주 시. 부족하면 `TimeoutException`/`BufferExhausted` |
| `compression.type` | 클라이언트 압축 | 네트워크·디스크 절감. `lz4`/`zstd`가 실무에서 무난한 선택지 |
| `max.request.size` | 요청(배치) 최대 크기 | 큰 메시지 전송 시. 브로커/토픽 `message.max.bytes`와 **반드시 정합** |
| `request.timeout.ms` | 단일 요청 타임아웃 | 브로커 응답이 느린 환경. `delivery.timeout.ms`보다 짧게 |
| `partitioner.class` | 파티셔너 | 기본 해시 파티셔너. 커스텀 샤딩·라운드로빈이 필요할 때 |
| `transactional.id` | 트랜잭션 프로듀서 ID | **읽기-처리-쓰기**를 하나의 트랜잭션으로 묶는 Exactly-once 파이프라인 |

## 5. 컨슈머 설정 — 리밸런스와 커밋이 안정 운영의 핵심

컨슈머에서 가장 많이 터지는 이슈는 **"느린 처리 → 리밸런스 폭풍 → 중복 처리/지연"** 입니다. 설정도 중요하지만, **처리 시간 예산을 지키는 것**이 더 중요합니다.

### 📌 핵심 프로퍼티

| 프로퍼티 | 설명 | 이런 상황에 주로 사용 |
|---|---|---|
| `bootstrap.servers` | 초기 브로커 목록 | 프로듀서와 동일하게 복수 지정 |
| `group.id` | 컨슈머 그룹 ID | 동일 목적의 소비자들을 하나의 그룹으로. **목적별로 그룹을 분리** |
| `key.deserializer` / `value.deserializer` | 역직렬화기 | 프로듀서 직렬화와 쌍을 맞출 것 |
| `enable.auto.commit` | 자동 오프셋 커밋 | 실무 권장 **`false` + 수동 커밋**. 처리 전 커밋되면 유실, 처리 후 실패 시 중복 가능 → 앱 멱등성 필수 |
| `auto.offset.reset` | 커밋된 오프셋이 없을 때 시작 위치 (`earliest`/`latest`) | 신규 그룹이 과거부터 재생 → `earliest`, 실시간만 → `latest` |
| `max.poll.records` | 한 번 `poll()`로 가져올 최대 레코드 수 | 처리가 무거운 컨슈머는 **줄여서** `max.poll.interval.ms` 초과를 방지 |
| `max.poll.interval.ms` | poll 사이 최대 허용 시간 | 배치·외부 API 호출이 긴 작업. 초과 시 **강제 리밸런스** |
| `session.timeout.ms` | 세션 타임아웃 | 브로커가 컨슈머 생존을 판단. 너무 짧으면 일시 GC에도 탈락 |
| `heartbeat.interval.ms` | 하트비트 주기 | 보통 `session.timeout.ms`의 1/3 이하 |
| `fetch.min.bytes` / `fetch.max.wait.ms` | 브로커가 응답하기 전 최소 데이터/대기 | 처리량 중시 시 `fetch.min.bytes`를 키워 요청 수 감소 |
| `max.partition.fetch.bytes` | 파티션당 최대 fetch 크기 | 큰 메시지·메모리 사용량 조절 |
| `isolation.level` | `read_uncommitted` / `read_committed` | 트랜잭션 프로듀서 사용 시 **`read_committed`** |
| `partition.assignment.strategy` | 파티션 할당 전략 | Cooperative Sticky 등으로 **리밸런스 시 Stop-the-world**를 줄일 때 |
| `client.id` | 클라이언트 식별자 | 모니터링·쿼터·로그 추적에 유용 |

### 📌 컨슈머 스레드·동시성 설정

카프카 클라이언트 API의 `KafkaConsumer`는 **스레드 세이프하지 않습니다.**  
즉 `poll()` / `commit()` / `close()` 는 **한 컨슈머 인스턴스당 하나의 스레드**가 소유해야 합니다.  
병렬 처리는 “한 컨슈머를 여러 스레드가 공유”가 아니라, **컨슈머(스레드)를 여러 개 띄워 파티션을 나눠 갖는 방식**으로 만듭니다.

```
[잘못된 감각]
KafkaConsumer 1개 ──(여러 워커 스레드가 동시에 poll/commit)──► ❌ 경쟁·깨진 오프셋

[올바른 기본 패턴]
파티션 12개 토픽
  ├─ Consumer-Thread-0 (파티션 0,1,2,3)
  ├─ Consumer-Thread-1 (파티션 4,5,6,7)
  └─ Consumer-Thread-2 (파티션 8,9,10,11)
→ 동일 group.id, 인스턴스(또는 concurrency) 수 ≤ 파티션 수
```

| 설정 / 개념 | 설명 | 이런 상황에 주로 사용 |
|---|---|---|
| **파티션 수** | 동일 컨슈머 그룹의 **최대 병렬도 상한** | 스레드를 늘리기 전에 먼저 확인. 스레드(컨슈머) > 파티션이면 **유휴 컨슈머**만 생김 |
| Spring `concurrency` (`ConcurrentKafkaListenerContainerFactory#setConcurrency`) | 리스너 컨테이너 안에서 **독립 Consumer를 N개** 생성 | 단일 앱 프로세스에서 파티션 병렬 소비. 예: 파티션 12 → `concurrency=6`이면 인스턴스당 6개 스레드 |
| `spring.kafka.listener.concurrency` | 위 concurrency의 application.yml 설정 | Spring Boot에서 환경별(로컬 1, 운영 6)로 조절할 때 |
| `group.instance.id` (Static Membership) | 컨슈머를 정적 멤버로 등록 | 배포·재시작 시 **불필요한 리밸런스**를 줄이고, 스레드/파드 수를 안정적으로 유지할 때 |
| Kafka Streams `num.stream.threads` | 스트림 앱 내부 스트림 스레드 수 | Streams 토폴로지를 **프로세스 안에서** 병렬 처리할 때 (태스크 ≤ 파티션 제약과 동일) |
| 처리용 워커 스레드 풀 (poll 스레드와 분리) | poll은 1스레드, 비즈니스만 스레드 풀 | I/O 대기가 긴 외부 API 호출. **커밋 시점·순서·실패 전파를 직접 설계**해야 해서 난이도↑ |

#### 💡 Spring Kafka concurrency 예시

```yaml
# application.yml
spring:
  kafka:
    consumer:
      group-id: order-consumer
      enable-auto-commit: false
      max-poll-records: 100
    listener:
      ack-mode: record          # 또는 batch — 커밋 단위와 맞춤
      concurrency: 6            # 프로세스 내 컨슈머 스레드 6개
```

```java
@Bean
ConcurrentKafkaListenerContainerFactory<String, Object> kafkaListenerContainerFactory(
        ConsumerFactory<String, Object> consumerFactory) {
    ConcurrentKafkaListenerContainerFactory<String, Object> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
    factory.setConsumerFactory(consumerFactory);
    factory.setConcurrency(6); // 파티션 수 이하로. 과도하면 리밸런스·유휴만 증가
    factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
    return factory;
}

@KafkaListener(topics = "order.created", groupId = "order-consumer")
public void onMessage(ConsumerRecord<String, Object> record, Acknowledgment ack) {
    // 각 concurrency 슬롯이 독립 Consumer + 전용 스레드로 이 메서드를 호출
    process(record);
    ack.acknowledge();
}
```

#### 💡 스레드 수를 정하는 실무 감각

1. **상한**: `concurrency × (앱 인스턴스 수) ≤ 토픽 파티션 수`  
   - 예: 파티션 12, 파드 2대 → 파드당 concurrency는 **최대 6**
2. **시작값**: CPU·외부 I/O에 따라 다르지만, 파티션의 **1/2 ~ 전체** 범위에서 lag를 보며 증설
3. **늘리기 전 확인**: lag가 높은데 CPU는 놀고 있으면 concurrency 증설 후보. CPU·DB 풀이 이미 포화면 스레드만 늘려도 의미 없음
4. **poll 스레드와 워커 분리 시 주의**  
   - 워커가 아직 처리 중인데 poll 스레드가 먼저 커밋하면 → **유실**  
   - 커밋은 했는데 워커가 실패하면 → **미처리(또는 DLT로 보내기 전 공백)**  
   - 파티션 내 순서 보장이 필요하면, 키/파티션 단위로 워커를 직렬화하거나 **아예 concurrency(다중 컨슈머) 패턴**을 우선

```
[권장] 병렬 = 컨슈머 스레드(concurrency) 증가
  · 오프셋·리밸런스·순서(파티션 단위)를 카프카가 관리

[고급] poll 1 + worker N
  · 처리량 극대화 가능하지만 커밋/실패/순서 책임을 앱이 짐
  · 가능하면 Retry/DLT·멱등성과 함께 설계
```

#### 💡 JDK 21 Virtual Thread + Spring Kafka (짧게)

Virtual Thread는 **I/O 대기(DB·외부 API·다른 카프카 produce)** 가 긴 리스너에서 플랫폼 스레드 고갈을 줄이는 데 유리합니다.  
다만 **카프카 병렬도의 상한은 여전히 파티션**이고, Virtual Thread가 파티션 수 제한을 없애 주지는 않습니다.

```yaml
# Spring Boot 3.2+ / JDK 21
spring:
  threads:
    virtual:
      enabled: true   # Tomcat 등 웹 요청에 가상 스레드 적용
  kafka:
    listener:
      concurrency: 6  # 여전히 "컨슈머 개수" — 파티션 한도 내에서
```

```java
// 리스너 실행만 가상 스레드로 돌리고 싶을 때 (Boot/Spring Kafka 버전에 따라 지원)
factory.getContainerProperties()
        .setListenerTaskExecutor(new VirtualThreadTaskExecutor("kafka-vt-"));
```

실무에서 기억할 점:

1. **`concurrency`는 그대로 유효** — Virtual Thread ON이어도 컨슈머/파티션 할당 모델은 동일
2. **효과가 큰 곳** — 리스너 안에서 blocking I/O가 많은 경우 (대기 중 캐리어 스레드 양보)
3. **효과가 작은 곳** — CPU 바운드 파싱/암호·순수 연산. 오히려 파티션·배치(`max.poll.records`) 튜닝이 우선
4. **커넥션 풀 한도** — 가상 스레드가 많아져도 JDBC/HTTP 풀 크기를 넘으면 대기만 늘므로, DB 풀·HTTP 클라이언트 한도를 함께 맞춤
5. **순서·커밋** — Virtual Thread로 워커를 무한 늘리는 패턴보다, **concurrency로 파티션 병렬**을 유지하는 쪽이 운영이 단순함

### 💡 안전한 소비 루프 (개념)

```
1. poll() 로 레코드 배치 수신          ← 컨슈머당 전용 스레드
2. 레코드별 비즈니스 처리 (멱등 키/유니크 제약으로 중복 방어)
3. 성공한 범위만 수동 commitSync/commitAsync
4. 실패 시 Retry 토픽 발행 또는 ErrorHandler → DLT
5. poll 주기와 처리 시간이 max.poll.interval.ms 를 넘지 않게 유지
6. 병렬이 필요하면 concurrency/인스턴스를 늘리되 파티션 수를 넘지 않기
```

### 💡 상황별 추천

```properties
# A) 일반 비즈니스 컨슈머 (권장 기본)
enable.auto.commit=false
auto.offset.reset=earliest
max.poll.records=100
max.poll.interval.ms=300000
# Spring: spring.kafka.listener.concurrency = min(파티션수/인스턴스수, 적정값)

# B) 무거운 배치/외부 연동 컨슈머
max.poll.records=20          # 한 번에 적게
max.poll.interval.ms=900000  # 처리 예산에 맞게 확대
# concurrency는 무리하게 키우지 말고, 외부 API 타임아웃·커넥션 풀과 함께 튜닝

# C) 트랜잭션 파이프라인 소비자
isolation.level=read_committed
enable.auto.commit=false

# D) Kafka Streams
# num.stream.threads=4   # 프로세스 내부 스트림 스레드 (태스크/파티션 한도 내)
```

## 6. 장애 발생 대책 및 시나리오

설정만으로 장애가 사라지지는 않습니다. **"어떤 장애가 나면 무엇이 깨지고, 무엇이 버티는지"** 를 시나리오로 미리 적어 두는 것이 운영 문서의 핵심입니다.

### 시나리오 1) 브로커 1대 장애

```
조건: replication.factor=3, min.insync.replicas=2, unclean.leader.election=false
결과:
  · 해당 브로커의 리더 파티션은 남은 ISR 중 새 리더 선출
  · acks=all 쓰기는 계속 가능 (ISR ≥ 2)
  · 장애 브로커의 디스크 데이터는 복구/재투입 후 팔로워로 따라잡기(Catch-up)
대책:
  · 랙/AZ 인지(rack-aware) 배치로 동시 장애 확률 감소
  · 모니터링: UnderReplicatedPartitions, ISR shrink/expand, 리더 선출 횟수
```

### 시나리오 2) 브로커 2대 동시 장애 (RF=3 클러스터)

```
조건: 특정 파티션의 ISR이 1 이하로 감소 가능
결과:
  · min.insync.replicas=2 이면 acks=all 프로듀서는 **쓰기 실패**(NotEnoughReplicas)
  · 읽기는 리더가 살아 있으면 가능할 수 있음
대책:
  · 다중 AZ/랙에 복제본 분산
  · 프로듀서 측 재시도 + 애플리케이션 Circuit Breaker/대기열
  · "쓰기 실패를 성공으로 포장하지 않기" (사용자/상위에 명확한 실패 전달 또는 아웃박스 재시도)
```

### 시나리오 3) 컨트롤러(KRaft) 장애

```
조건: 컨트롤러 3대 중 1대 장애
결과:
  · 과반수(2/3) 유지 → 새 Active Controller 선출, 메타데이터 운영 지속
  · 컨트롤러 2대 동시 장애(3대 구성) → 쿼럼 상실 → 파티션 변경/토픽 생성 등 메타데이터 작업 불가
대책:
  · 프로덕션은 Isolated 컨트롤러 + 홀수 쿼럼
  · 컨트롤러와 브로커의 롤링 재시작 창을 분리
  · 메타데이터 디스크·커밋 지연(Commit latency) 모니터링
```

### 시나리오 4) 디스크 Full / 느린 디스크

```
결과:
  · 해당 브로커 쓰기 지연 → 복제 랙 → ISR에서 탈락 가능
  · 페이지 캐시 효율 저하, 클라이언트 타임아웃 증가
대책:
  · retention / disk usage 알람 (예: 80% 경고, 90% 심각)
  · 토픽별 retention 차등, 불필요 토픽 정리
  · 로그 디렉터리 다중 디스크, OS/JVM/페이지 캐시 여유 확보
```

### 시나리오 5) 컨슈머 장애·리밸런스 폭풍

```
증상:
  · max.poll.interval.ms 초과, 잦은 배포, 세션 타임아웃
  · 파티션 재할당 반복 → 처리 지연(lag) 급증, 중복 소비 증가
대책:
  · max.poll.records 축소, 처리 시간 프로파일링
  · Cooperative rebalance / 정적 멤버십(group.instance.id) 검토
  · 배포 시 group.initial.rebalance.delay.ms, 롤링 배포
  · 컨슈머 멱등성 + DLT로 "한 건이 파티션을 영구 차단"하는 Poison Pill 방지
```

### 시나리오 6) Poison Pill (독 메시지)

```
증상:
  · 특정 레코드만 역직렬화/비즈니스 예외 → 같은 오프셋에서 무한 실패
  · 파티션 전체가 멈춘 것처럼 보임 (lag만 증가)
대책:
  · 최대 재시도 후 DLT로 격리
  · DLT 알림(슬랙/페이저) + 원본 헤더 보존
  · 스키마 호환성(Backward/Forward) 검증을 CI에 포함
```

### 시나리오 7) 프로듀서 중복 전송

```
원인: 브로커는 저장했는데 응답 타임아웃 → 프로듀서 재시도
대책:
  · enable.idempotence=true
  · 필요 시 transactional.id
  · 컨슈머/DB 쪽 비즈니스 키 멱등 처리 (최종 안전망)
```

### 🛠️ 장애 대응 체크리스트 (운영용)

1. **증상 확인**: 프로듀서 에러율, 컨슈머 lag, URP(Under Replicated Partitions), ISR, 디스크, GC
2. **영향 범위**: 특정 토픽/파티션인지, 클러스터 전체인지
3. **데이터 안전 우선**: `unclean.leader.election`을 급하게 켜서 가용성만 확보하지 말 것
4. **재처리 전략**: 오프셋 리셋은 최후 수단. DLT·Retry·아웃박스 우선
5. **사후**: 타임라인, 근본 원인, 알람 임계값·런북 업데이트

## 7. 대기업은 어떻게 구성할까? — Netflix & LinkedIn 참조

설정 튜닝을 "정답 한 줄"로 외우기보다, **대규모 조직이 어떤 운영 원칙을 택했는지**를 보면 의사결정이 쉬워집니다.

### 🎬 Netflix (Keystone 파이프라인)

넷플릭스는 회원 행동 이벤트(재생, 검색, 노출 등)를 수집하는 **Keystone** 파이프라인의 입구에 카프카를 둡니다.

공개 자료에서 반복되는 원칙:

1. **거대 단일 클러스터 대신 작은 클러스터 다수**
   - 클러스터당 브로커를 대략 **200대 미만**으로 제한해 장애 반경을 줄입니다.
2. **Fronting Kafka / Consumer Kafka 2계층**
   - Fronting: 전 서비스 프로듀서 수집·버퍼링  
   - Consumer: 실시간 소비 워크로드용으로 라우팅된 토픽 서브셋
3. **파티션 수 상한 관리**
   - 클러스터당 파티션을 과도하게 키우지 않음 (요청 지연·가용성에 파티션 수가 직접 영향).
4. **파티션 처리량 가정치**
   - 계획 시 **파티션당 약 0.5~1 MB/s** 수준을 보수적으로 잡았다는 실무 사례가 공유됩니다. (병목은 브로커보다 컨슈머인 경우가 많음)
5. **설정 변경을 ‘장애 훈련’처럼 취급**
   - 키 기반 토픽의 파티션 수를 라이브에서 함부로 `alter`하지 않고, **신규 클러스터/토픽으로 페일오버**하는 방식에 가깝게 운영합니다.
6. **클라우드(AWS) 최적화**
   - Rack-aware 파티션 배치로 AZ 간 전송 비용·지연을 줄이는 방향으로 기여/운영해 왔습니다.

> 참고: [Kafka Inside Keystone Pipeline (Netflix TechBlog)](https://netflixtechblog.com/kafka-inside-keystone-pipeline-dd5aeabaf6bb)

### 💼 LinkedIn (Kafka의 고향)

링크드인은 카프카를 처음 만든 회사이며, 공개 시점 기준 **하루 수조 건, 100+ 클러스터, 수천 브로커, 수백만 파티션** 규모로 운영해 온 것으로 알려져 있습니다.

핵심 운영 패턴:

1. **워크로드별 클러스터 분리**
   - 활동 추적, DB 복제(Espresso), 메트릭 등 **목적별 클러스터**로 blast radius와 튜닝 포인트를 분리
2. **멀티 데이터센터 + 계층형 토폴로지**
   - 로컬 생산 → Aggregate 클러스터로 집약 → 각 DC 로컬 소비  
   - DC 간 복제를 최소화하는 방향의설계
3. **MirrorMaker → Brooklin Mirror Maker**
   - 단순 MirrorMaker 다중 파이프라인의 운영 한계를 극복하기 위해 내부 미러링 플랫폼으로 진화
4. **Cruise Control**
   - 파티션 재배치·목표 기반 밸런싱을 자동화해 수작업 리밸런스의 한계를 보완
5. **파티션 단위 관측**
   - 토픽 평균값이 아니라 **파티션별 처리량/랙**을 봐야 핫스팟을 잡을 수 있다는 교훈

> 규모 숫자는 발표 시점에 따라 달라지므로, "링크드인급 = 멀티 클러스터 + 자동화 + 워크로드 격리"라는 **원칙**을 가져가는 편이 안전합니다.

### 🏢 우리 서비스에 적용할 수 있는 공통 교훈

| 대기업 원칙 | 중소~중규모 서비스에 번역하면 |
|---|---|
| 작은 클러스터 다수 | 핵심 거래 클러스터와 로그/분석 클러스터를 **물리/논리 분리** |
| 파티션 보수적 산정 | 키 토픽은 처음부터 여유 있게, 라이브 `alter`는 최후 수단 |
| Rack/AZ 인지 | `broker.rack` + 복제본 분산으로 동시 장애 대비 |
| 자동화 | 최소 알람(lag, URP, disk) + 가능하면 Cruise Control류 도입 |
| 변경은 페일오버처럼 | 토픽/파티션/설정 변경 절차를 런북으로 고정 |

## 8. 실무에서 바로 쓰는 최소 체크리스트 ✅

### 클러스터(KRaft + Broker)

- [ ] 프로덕션은 **Controller / Broker 역할 분리**, 컨트롤러 **3대**
- [ ] `default.replication.factor=3`, `min.insync.replicas=2`
- [ ] `unclean.leader.election.enable=false`
- [ ] `auto.create.topics.enable=false`
- [ ] `__consumer_offsets` / 트랜잭션 로그 복제본 **3**

### 토픽

- [ ] 파티션 수는 컨슈머 병렬도·MB/s 기준으로 산정 (축소 불가!)
- [ ] 중요 토픽은 `min.insync.replicas=2` 명시
- [ ] Retry / DLT 토픽과 헤더 규약 준비

### 프로듀서

- [ ] 유실 민감: `acks=all` + `enable.idempotence=true`
- [ ] `delivery.timeout.ms` / `linger.ms` / `compression.type` 트래픽에 맞게 튜닝

### 컨슈머

- [ ] `enable.auto.commit=false` + 수동 커밋
- [ ] `max.poll.records` ↔ `max.poll.interval.ms` 예산 맞추기
- [ ] **concurrency × 인스턴스 수 ≤ 파티션 수** (유휴 컨슈머 방지)
- [ ] `KafkaConsumer`를 여러 스레드가 공유하지 않기 (1 컨슈머 = 1 poll 스레드)
- [ ] 애플리케이션 **멱등성** + Poison Pill → DLT

### 관측/장애

- [ ] lag, URP, ISR, disk, request latency 알람
- [ ] 브로커 1대 장애 / 컨트롤러 1대 장애 Failover 정기 훈련

## 9. 마치며 & 요약 정리

1편에서 개념과 용어를 쌓았다면, 2편은 **"설정값이 곧 장애 내성 설계"** 라는 이야기에 가깝습니다.

- **KRaft**: 프로덕션은 Isolated 컨트롤러(3/5) + 리스너 분리 + 빠른 메타데이터 디스크
- **브로커**: RF=3, `min.insync.replicas=2`, unclean leader 금지, 자동 토픽 생성 OFF
- **토픽**: 파티션은 신중히, Retry/DLT로 실패를 **격리**
- **프로듀서**: 유실 방지 3종 세트(`acks=all` + 멱등 + min ISR) + 배치/압축으로 처리량 확보
- **컨슈머**: 수동 커밋, poll 예산 관리, **concurrency로 병렬화(파티션 한도)**, 앱 멱등성
- **장애**: 가용성을 위해 유실 스위치를 함부로 켜지 말고, 시나리오·런북·알람으로 대비
- **대기업 교훈**: 단일 거대 클러스터보다 **분리·자동화·보수적 파티션·변경 절차**

다음 편에서는 원하시면 **스키마 레지스트리·보안(SASL/SSL)·모니터링(JMX/Prometheus)·Cruise Control** 같은 운영 심화로 이어가 보겠습니다.
